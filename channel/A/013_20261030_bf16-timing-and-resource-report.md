# A/013：BF16 S1 上线后的**全套实测**——上电、语音、编码、UI 各花多少

> ⚠️ 板子没有 RTC，`date` 恒显示 `2026-09-22`。本文所有"相对上电"的秒数是用
> `now - /proc/uptime` 反推开机时刻后算的，**不受假日期影响**；引用的日志时间是板端时间。

## 0. 一句话

换成 BF16 S1 之后：**画质 26.61 dB（vs 坏 int8 的 8.07 dB，口径见 §4）、稳态编码 0.98 s/张、
语音识别在噪声范围内不变（RTF 0.813–0.836）、引擎载入多 8.82 s、内存仍有余量（可用 313–325 MB）**。

> 「8.82 s」是**引擎载入**之差（18.26 − 9.44），不是端到端上电之差；
> 端到端上电时间见 §1，其中「能发图」约 **+41 s**。

## 1. 上电时间（干净重启一次，BF16 配置）

| 里程碑 | 相对上电 |
|---|---:|
| **SSH 可用**（网络栈通） | **27 s** |
| KWS 开始监听 | 18 s |
| **UI 首帧就绪** | **23 s** |
| **引擎就绪**（能立刻发图） | **约 41 s** |
| UI 启动完成（预热哨兵 `/dev/shm/glc_ui_boot_done`） | **45 s** |
| ASR 可用（模型加载完） | **约 47 s** |

口径说明（这几行能对上，是因为都换算成"相对上电"）：

- **SSH 那一行**：PC 侧每 3 s 轮询一次，且我在触发重启后先 sleep 5 s 才开始轮询
  ⇒ 真实值在 **22–27 s** 之间，取 27 s 是上界。
- **UI 首帧 23 s**：`/dev/shm/glc_ui_ready` 的 mtime 与"上电时刻"（`now − /proc/uptime`）之差。
- **daemon 启动时刻**：`start_ui.sh` 在 UI 首帧之后才调 `boot_warm()` 起 daemon，
  所以 daemon 是 **≈ +23 s** 起的；它自己载入 18.26 s
  ⇒ **引擎就绪 ≈ 23 + 18.26 ≈ +41 s**（串行相加，两者几乎没有重叠）。
- **ASR 可用 ≈ +47 s**：`asr_preload.sh` 等 UI 首帧哨兵（23 s）+ 自身 2 s 起跑延迟 + 模型 21.55 s。

## 2. 引擎载入明细（BF16，冷启动）

```
Engine: s1   s1_encoder_ga_hyper   json 1.44s  lazy 13.23s  sess 0.23s  apply 0.78s
Engine: s2   s2_hyperdec_fusion    用 flat 载入 0.33 s
Engine: s3p1 s3_phase1             用 flat 载入 0.19 s
Engine: s3p2 s3_phase2             用 flat 载入 0.19 s
Engine: s3p3 s3_phase3             用 flat 载入 0.19 s
Engine: ★ 5 个子图全部就绪，一次性总成本 18.260 s
```

**明细要对齐一下**：上面每个子图那行 `用 flat 载入 / json … apply …` 里，
`json/lazy/sess/apply` 四段才是该子图的全部成本。按此重算：

| 子图 | 各段之和 |
|---|---:|
| s1 | 1.44 + 13.23 + 0.23 + 0.78 = **15.68 s** |
| s2 | 0.33 + 0.00 + 0.01 + 0.55 = **0.89 s** |
| s3 ×3 | (0.19 + 0.00 + 0.01 + 0.33) × 3 = **1.59 s** |
| 合计 | **18.16 s**（日志报 18.260 s，余下 ≈0.1 s 是 Device.Open 等，未逐项列出） |

**BF16 的增量主要在 s1**：这次 s1 单项 15.68 s，其中 `lazy 13.23 s`（读 290 MB 权重）。
作为对照，int8 那次实测 s1 单项是 `json 3.30 + lazy 1.97 + sess 0.18 + apply 0.90 = 6.35 s`，
整机 `一次性总成本 9.442 s`。

⏱ **注意两次不是同一时刻测的**（int8 那次页缓存状况不同），所以：

- 可直接引用的差：**整机 18.26 − 9.44 = 8.82 s**；
- 不宜说「差别只在 lazy」——int8 的 `json` 段也到了 3.30 s，不是 1.44 s。

## 3. 语音识别：**不受影响**

同一段自检音频（5.59 s，识别结果 `开饭时间早上9点至下午5点。`）：

| 条件 | 模型载入 | 识别耗时 | RTF |
|---|---:|---:|---:|
| 引擎完全没跑 | 20.8 s | **4.675 s** | **0.836** |
| BF16 引擎常驻（空闲） | 16.5 s | 4.547 s | 0.813 |
| **BF16 引擎正在连续编码** | 19.6 s | **4.673 s** | **0.836** |

**结论**：边编码边说话，识别耗时与"完全没有引擎"一致（4.673 vs 4.675 s，差 0.04%）。
中间那行（引擎空闲）是 4.547 s / RTF 0.813，比另两行低约 2.7%——
**六次重复里只测到一次**，我按噪声处理，不当成"引擎让语音变快"。
载入时间那列的 16.5/19.6/20.8 差异同样**来自页缓存冷热**，不是引擎。

## 4. 编码耗时

| 场景 | 数值 | 口径 |
|---|---:|---|
| **稳态单张（daemon 内部）** | **0.98 s** | `[BATCH] … enc 0.977 s / prep 0.009 s`（实测） |
| 端到端（含脚本与自检） | 1419 ms | UI/ASR/KWS 同时在线（实测） |
| **冷启动后第一张** | **2.0 s** | 模型页首次换入（实测） |
| int8 对照 | 0.57 s | 同一张图、同一套链（实测） |
| 坏 int8（`compile_real`）对照 | 0.639 s | 但产出 292 B 红图 |

PSNR 口径（两个 dB 值都出自这一口径）：
**解码图 vs 该图 256×256 无损 PNG 原图，峰值 255、整幅 RGB、uint8**；
解码用 `pc_decode_selfcontained.py`（只吃容器）。
`320 B`（BF16）→ **26.61 dB**；`292 B`（坏 int8）→ **8.07 dB**。

| 项 | 值 | 来源 |

## 6. 内存（四进程同时在线）

| 进程 | RSS |
|---|---:|
| `glc_asr_service`（SenseVoice int8 228 MB 模型） | 303 MB |
| `glc_ui.py` | 82 MB |
| `glcenc_daemon`（**BF16 S1 常驻**） | 96 MB |
| `glc_kws.py` | 59 MB |
| 四进程 RSS 合计 | 540 MB |
| 系统合计（`free -m`） | used 594–607 MB / **可用 313–325 MB** / 总量 **993 MB** |

**无 OOM**。三点口径：

- 四进程 RSS 合计 540 MB，而 `free` 的 used 是 594–607 MB
  ⇒ 差的 **54–67 MB** 是系统进程（sshd、`gige_grab`、`cam_watch` 等）与内核，未逐项列出。
- `used + available` 不等于 993 MB，因为 **buff/cache 单列**（约 200 MB）且其中大部分可回收；
  available 已经把可回收部分算进去了。
- BF16 的 290 MB 权重主要是**文件页**（page cache），RSS 里不含全量；
  真正吃匿名内存的是 ASR 的 228 MB 模型。

## 7. 这轮同时修掉的两个坑（都在板端）

### 7.1 `models/flat/` 旧缓存覆盖 json/raw

`glc_rsd.py` 原本**优先**读 `models/flat/<name>.flat`，失败才回退 json+raw。
板上那份 s1 flat 是 09-22 由 **int8** 模型 dump 的（220,396,800 B），与 xir 版本绑定。
⇒ **换掉 json/raw 也不生效**，编出来仍是同一份 292 B 红图。

修法（已上线）：

1. flat 旁边放 `<name>.flat.meta`，记录 `json_md5` 与 `raw_size`；
2. 载入前比对，不同源就**忽略**并打日志（`!! flat 与当前模型不同源（…），忽略`）；
3. 走 json+raw 时**自动重建** flat，但**只对 raw ≤ 64 MB 的子图**做——
   两种"大小"别混：那份**旧 int8 flat 的成品文件是 220,396,800 B**；
   而**BF16 的 s1 raw 是 290,299,708 B**，把这个 dump 成 flat 会把进程 RSS 顶到 604 MB，
   实测被 OOM killer 杀过（`dmesg`：`Out of memory: Killed process python3`）；
4. 全程 try/except，任何失败只退化成"慢启动"，不影响起不来。

实测效果：s2/s3 第一次重建并写 meta（+0.24~0.64 s），第二次起回到 flat（0.03~0.06 s）。
