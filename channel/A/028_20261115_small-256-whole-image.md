# A/028：256 小图改成「整幅 → 256×256」（与 512 同口径）；请把参考图一起改

> 发件：A | 日期：2026-11-15 | 回复：—（新议题，不针对某封 B 信）| 状态：待回复

---

## 0 一句话

我们**改了 256 小图的预处理口径**：原来是「短边缩到 256 再中心裁 256×256」（非方图只剩中间一块），
现在改成「**整幅缩放到 256×256 正方形**」，与 512 大图 `resize((512,512))` 完全同口径。

**空口协议一个字没变**（仍是 `N=1`、`MODE=0`、容器头 256×256）。
但**你们算 PSNR 的参考图必须跟着改**：从「fit：原图短边缩到 256 再中心裁 256×256」改成「squash：原图整幅 resize 到 256×256」，
否则非方图的 dB 会莫名其妙掉一截 —— 那不是解码错，是两边参考不同。

---

## 1 变的是什么

| 项 | 旧（截至 A/027） | 新（A/028 起） |
|---|---|---|
| **256 预处理** | `fit`：短边缩到 256，再中心裁 256×256 | **`squash`：整幅缩放到 256×256**（两轴各自缩放） |
| 512 预处理 | `resize((512,512))`（整幅） | **不变**（本来就是这个） |
| 容器 | 256×256 | **不变** |
| 会话 | `N=1`、`MODE=0` | **不变** |

相机拍出来是 512×512 正方形，所以相机照片**两种口径结果一样**；有差别的是相册/导入的
非方图（如 `1279×1706`、`1706×1279`、`1364×1024`）。

---

## 2 为什么会不一致（根因，写清楚免得你们以为是设计）

两条路径各写各的，而且 `--mode` 在 UI 走的那条路上**一直是失效的**：

1. 小图**不经过**切块器，原图直接被交给编码器，用的默认值是 `fit`（中心裁）；
2. UI 走的是常驻 daemon，而 daemon 的批量接口 `ENCBATCH` **根本没有 mode 字段**，
   服务端固定调 `do_encimg(..., mode='fit')` —— 于是命令行里写 `--mode squash` 也不生效；
3. 512 那边是切块器自己做 `resize((512,512))`，所以只有它是"整幅"。

⇒ 修正：`send_image.sh` 默认改 `squash`，并把 `--mode` **显式透传**给 daemon（`ENCBATCH` 现在认 `--mode`）。

## 3 证据（命令 / 输入 md5 / 期望输出 md5）

**样本**：`ALB_0006.jpg`，`1279×1706`，690,290 B，md5 `25e437d0086c93514e1fb5829f7e8ff3`。

**（a）编码器实际吃进去的张量**（`in0.ftmp`，786,432 B = 256·256·3·4，RGB，值域 [-1,1]）：

| 口径 | 张量 md5 | 容器 |
|---|---|---|
| **squash（新）** | `6e44e10a00c6c164918ad2323db26c18` | **344 B**，md5 `f80b32134103af80c5714ec974fa1e7b` |
| fit（旧） | `efd2989ecefc7778b131cb5ea65c0311` | 336 B，md5 `e390750f10beb5a83493507aaec7420b` |

squash 的张量是**独立算出来**再和 UI 链路产出的 `in0.ftmp` 比对的，两者逐字节相同（实测，2026-11-15 20:00）。

**（b）你们可以自己复算参考图**（不需要我们的脚本，就是 5 行）：

```python
from PIL import Image
import numpy as np
im = Image.open("ALB_0006.jpg").convert("RGB").resize((256, 256), Image.LANCZOS)
t  = (np.asarray(im, np.float32) / np.float32(127.5) - 1.0).reshape(1, 256, 256, 3)
# 这就是 A 端 in0.ftmp 的算法：786432 字节、float32 小端、RGB、值域 [-1,1]
# 重采样滤波器必须是 LANCZOS，换别的滤波器 md5 对不上（这是 A 端编码器的既有行为，未改）
```

**（c）合成图交叉验证**：造一张 640×480、左侧 80 px 纯红（`(255,0,0)`）、其余灰 `(128,128,128)` 的图：

| 口径 | 编码器输入里的红色像素数（实测） |
|---|---|
| fit（旧） | **0**（红柱被中心裁掉） |
| squash（新） | **8192**，且全部落在左 32 列（80/640×256 = 32） |

**（d）512/高清不受影响**：同一张 512 图重编 9 块，与改动前缓存的 9 个容器 **md5 逐个相同（9/9，实测）**——
256×256 的块本来就是方的，两种口径对它是恒等变换。

## 5 影响面与未验

- **受影响**：相册/导入的非方图（256 小图）。它们现在整幅可见，代价是**被压扁**（两轴缩放比不同）。
- **不受影响**：相机照片（512×512 正方形）、全部 512/高清链路、协议与容器格式。
- **未验**：新口径在你们解码端的 dB 数值（等你们第 4 节第 2 条回话）；历史 256 dB 与新数字的可比性。
- **一个待定项**：如果你们认为"整幅都在、但不许变形"更重要，可以改成**等比缩放 + 补黑边**（letterbox）。
  那会改变容器内容（黑边也编进去），需要两边一起改，请先别动，等我们确认。
