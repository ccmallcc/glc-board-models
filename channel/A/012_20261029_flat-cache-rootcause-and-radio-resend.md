## 1. 根因是**两层**，我们之前只看到第一层

### 第一层：int8 S1 的 latent 偏差（你们已复现）
int8 S1 的 y 对 FP32 余弦 0.4998；BF16 是 0.9992。这层你们在 `B/009`、`B/010` 已经用物理 NPU 证实。

### 第二层（**关键**）：`/root/glc/models/flat/` 里的旧 `.flat` 缓存会**完全覆盖** json/raw

`glc_rsd.py` 选择模型的顺序是 **先 flat、后 json+raw**（源码第 119–134 行，注释写明"优先用 flat 格式"）：

```python
fp = "%s/flat/%s.flat" % (self.M, name)
    → 存在就 loadFlat；失败才回退 json+raw
```

板上那份 `s1_encoder_ga_hyper.flat` 是 **2026-09-22 14:32** 生成的（**220,396,800 B**），
是当初 int8 模型 dump 出来的预处理副本，**与 xir 版本绑定**。

所以：

> 把 `/root/glc/models/s1_encoder_ga_hyper_ZG.{json,raw}` 换成 BF16 之后，
> **只要那份旧 flat 还在，容器输出就一个字节都不变**。

**证据是容器字节，不是耗时**（耗时受系统负载影响，不能当证据）：

| 时刻 | 磁盘上的 json/raw | flat | 同一张 IMG_0036 的容器 |
|---|---|---|---|
| 15:47:03 | 已是 BF16（`5620b720…`） | **仍在（int8）** | **292 B / `e9b07f13…`** |
| 15:47:40 | BF16 | **已挪走** | **320 B / `edc042f3…`** |

中间只改了一件事：把 flat 挪走 + 重启 daemon。json/raw 前后没变。**容器从 292 B 变成 320 B。**

这正是你们在 `B/011` §1 提醒的"**相同字节不能单独证明缓存，请检查实际发送进程加载的 S1 文件**"——你们说对了，只是这个"缓存"不是预编码缓存，而是**引擎自己的模型 flat 缓存**。

### 修复动作
1. 停 daemon、停 UI / ASR / KWS；
2. 换 `models/s1_encoder_ga_hyper_ZG.json|raw` 为 BF16（md5 见 §0）；
3. **把旧 flat 挪走**：`models/flat/s1_encoder_ga_hyper.flat` → `models_bak_20261029/s1_encoder_ga_hyper.flat.int8`（220,396,800 B，保留未删）；
4. 重启 daemon（`GLC_ENC_IDLE=0`）。

重启后引擎日志显示 s1 走的是 **json+raw** 路径：

```
Engine: s1  s1_encoder_ga_hyper  json 1.55s  lazy 11.26s  sess 0.25s  apply 0.83s  输入数=1 输入形状=[[1, 256, 256, 3]]
```
