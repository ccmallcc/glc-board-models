# A/004：S1 混合链实测——画质不掉，代价是 8 个字节和 10 秒

上封说"混合链画质不掉"是**推算**。现在测了。

## 1. 做法（可复跑）

```
fp32 S1（PyTorch CPU）──► y
                          ├─ int8 S2/S3（HostBackend，板端同款 _ZG）──► 先验 ──► rANS ──► 容器
                          └─ 解码侧同样用 int8 先验 ──► y_hat ──► fp32 S4 ──► 图
```

脚本 `派活/_q33_hybrid.py`。同一张 `IMG_0036.jpg`（md5 `38fe5408…`）、`q=0`、256×256。

## 2. 结果（实测）

| 链 | 容器 | bpp | PSNR（对原图） |
|---|---|---|---|
| 全 fp32（现发布 `verify/`） | 308 B | 0.03760 | 26.61 dB |
| **混合：fp32 S1 + int8 先验 + fp32 S4** | **316 B** | **0.03857** | **26.72 dB** |
| 全 int8（板端，另一批图，仅作量级参考） | 312–324 B | 0.03870 | 21.60 dB |

**混合链的 PSNR 比全 fp32 高 0.11 dB** —— 这不是"更好"，是同一个数量级里的抖动
（先验换了，`means` 变，`round(y·q−means)+means` 的舍入点跟着变，往哪边偏都有可能）。
**结论是"没掉"，不是"提升了"。**

## 3. 它真的能被标准 int8 解码器独立解开（实测）

用仓库里的 `AB板/…/pc_decode_selfcontained.py`（只吃容器、不喂旁路）解这个 316 B：

```
容器 316 B  bpp=0.03857  PSNR=26.72
解出的 PNG md5 = c7c2387589f27e9780868790a0fc1fcb
编码端自己解的 PNG md5 = c7c2387589f27e9780868790a0fc1fcb   ← 逐字节相同
```

⇒ **容器自洽**：任何跑同一套 `_ZG` 的实现（你们的 NPU、你们的 HostBackend、我们的 HostBackend）
都能逐字节解出同一张图。

## 4. 代价

| 项 | 数值 | 说明 |
|---|---|---|
| 容器 | 308 → **316 B**（**+2.6%**） | int8 先验略不如 fp32 准，熵编码多一点 |
| 编码耗时 | **+8 次子图调用 ≈ 9.6 s/帧**（实测） | 这是我们 PC 上的数；你们板端本来就在 NPU 上跑，没有这层额外开销 |
| 解码 | 不变 | 解码本来就要算先验 |

> 注意：如果只用 int8 先验、**不再发 fp32 版**，那 2.6% 是实打实的 bpp 代价；
> 但换来的是"板端能解"。这个交换值不值，取决于你们产线的容错要求，我们不下结论。

## 5. 一个必须说清的取舍

**混合容器只能被 int8 先验解，不能被 fp32 参考实现解**（先验不同源，必然失步）。
所以 S1 一旦上，就意味着：

- **生产/电台链路**用 int8 先验 → 板端与你们都能解；
- **对外那组 fp32 参考向量**（`verify/`，26.61 dB）与它**不是同一批容器**，两边都得留。

这正是我们现在 `verify/`（fp32）与 `verify-int8/`（int8）并列的原因，不是冗余。

## 6. 边界

1. **只测了 1 张图、只测 `q=0`**。要 4 张以上才能说统计上成立。下一步我们会补 Kodak 4 图。
2. 0.11 dB 的差在单张图上**不能**当作"混合链更好"的证据。
3. 我们没有在真板上跑这条混合链（只跑了 HostBackend）。按 `31_PC自洽解码实测_路A.md` §2.3，
   HostBackend 与真板在 S2 输出上逐位一致，但**那是 5 张 `_ZG` + 那批输入**的口径，不能外推。
