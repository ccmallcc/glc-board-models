## 2. 真正的根因：**计算后端**，不是进程、不是线程、不是精度

| 容器产自 | 解码设备 | 结果 |
|---|---|---|
| **CUDA**（= 我们 10-24 发布的那份） | CUDA **新进程** | **NaN** |
| CUDA | CPU | 12.84 dB |
| **CPU**（= 现在仓库里那份） | **CPU 新进程** | **26.61 dB** |
| CPU | CPU `threads=1` | 26.61 dB，PNG **md5 完全相同** |
| CPU | CUDA | NaN |

两条铁证：

1. 用 `--device cuda` **重编**同一张图，得到容器 md5 `a267448bfee84958e0dd55501547b3e7`，
   与 10-24 发布的那份**逐字节相同** ⇒ 文件没坏，字节可复现。
2. 用 `--device cpu` 重编，得到 md5 `5b2a4571e1f605d36a3193c1b354eaed`，
   换一个进程解 = 26.61 dB，PNG 与发布的 `rec.png` 逐字节相同。

**机制**：`GLC2` 不存 scales/means，解码端必须重算。cuDNN 的**算法自动选择不是跨进程确定的**，
所以 CUDA 产的容器连 CUDA 自己新开进程都解不开；CPU 路径是确定的，所以稳。

> ⚠️ **口径更正（2026-10-25，审计 Q32A 第 3 条）**：上面这句里，**实测的是现象的四个角**
> （CUDA→CUDA 新进程 = NaN、CUDA→CPU = 12.84 dB、CPU→CPU 新进程 = 26.61 dB、CPU→CPU 单线程 = 同 md5），
> **"cuDNN 算法自动选择随进程变"是推断，不是实测** —— 我们没有直接观测 cuDNN 选算法的过程。
> float64 对照只排除了"精度"这一个替代解释，没有排除其它可能（例如 cuDNN 的 workspace/实现选择）。
> 准确的表述：**"现象已实测；机制是推断，倾向 cuDNN 非确定性"**。

我们还试过"先验走 float64"想把 CUDA 那份救回来 —— **救不回**（CPU 12.84 dB / CUDA NaN）。
这说明差异不是浮点精度造成的（实测）；至于是不是 cuDNN 选算法，**未验**。

## 3. 这条对你们的 13.19 dB 意味着什么

分三种情况，结论完全不同：

| 你们的解码后端 | 13.19 dB 说明什么 |
|---|---|
| **CPU torch**（与我们同栈） | 那就不是后端问题，是别的地方（模型版本 / 胶水 / 转置），**请按 §4 的 Q2 提供信息，我们一起查** |
| **CUDA** | 与容器后端不匹配，**不是你们的 bug** |
| **NPU int8（`_ZG` 子图）或手写 C** | **必然对不上**：fp32 容器需要 fp32 先验，量化链永远算不出同一组 scales/means。这不是实现问题，是口径问题 |

第三种情况下，无论你们怎么调，fp32 容器都解不出来 —— 所以我们要先知道是哪一种。
