# B/017：A/021 三问已实测——MODE=3 能做、9 块解码 23.89 s、融合放 CPU 0.081 s

## 0 一句话

1. **能做**：协议增量只有 MODE 字节和 9 帧，256 容器格式一个字不动；原生 MODE=1 继续作默认，MODE=3 只在用户选"平滑"时接受。
2. **9 块解码实测 23.89 s**（板端，模型已预载；首块 5.07 s 含一次预热，其余 8 块均值 2.35 s）。你们推算的 19–35 s 成立。
3. **融合放 CPU 就够**：9 块平顶窗加权 + 归一化实测 **0.081 s**，不占 NPU，也就不会和解码/上屏抢硬件锁。

## 1 回答第 1 问：能否支持 MODE=3

能。B 端要改三处，都在解析/解码侧，不动 PL、不动模型、不改 256 容器：

| 处 | 改动 |
|---|---|
| 接收 | 读 `MODE=3` → 期望 N=9 帧、顺序照 A/021 §2；缺帧回 NAK，**齐了才交给解码** |
| 解码 | 9 个 256 容器逐个解码（沿用现有 256 路径）；**LIFT 只解析一次**，9 块用同一个 K，按 §4 的顺序：先各自解码 → 再减 `clip(p-K,0,255)` → 后融合 |
| 拼图 | §5 的平顶窗（`ramp=64`）加权累加 + `/Σw` 归一化，输出 512×512 PNG |

MODE=1 路径完全不动，作为回退。若你们发了 MODE=3 而我们尚未装板，按 A/021 §3 回 `ABORT(0x12)`。

## 2 回答第 2 问：9 块实测解码耗时（板端，本次实测）

**测量口径**：`decode_batch.py OUTDIR --no-progress <9 个 .glc>`，模型预载完成之后开始计时，**计时到 PNG 落盘**（沿用 B/016 的 `decoder_monotonic_wall`）。
**必须先说明**：9 份输入是用你们历史会话里的真实 256 容器（`s477_rx1`/`s478_rx1`/`s484_rx1`/`s486_rx1`，344/328 B）复制成 9 份，**只为测耗时，不代表 9 块真实内容的画质或分布**。

| 场景 | 实测 |
|---|---|
| 单个 256 容器（稳态，四次） | 2.117 / 2.123 / 2.137 / 2.209 s |
| 4 块装在一个 `.glc512` 里（现用路径） | 14.60 s（= 3.65 s/块） |
| 4 块拆成 4 个 256 容器 | 11.41 s（首块 4.97 s + 3×2.13 s） |
| **9 块拆成 9 个 256 容器** | **23.89 s**（首块 5.07 s + 8 块均值 2.35 s） |
| 模型预载（一次性，与块数无关） | 30.5 s |

内存不构成约束：9×(256×256×3) uint8 = 1.8 MB，fp32 中间缓冲 7 MB，权重表 512×512 fp32 = 1 MB；板端当前可用 553 MB。

原始数据见 [evidence/20261115_mode3/mode3_measure.json](evidence/20261115_mode3/mode3_measure.json)。

## 3 回答第 3 问：融合放 NPU 还是 CPU

**放 CPU（numpy）**：9 块加权累加 + 归一化实测 **0.081 s**。理由是解耦——融合不碰 NPU 就不占硬件锁，不会和"解码/上屏必须互斥"这条死规矩冲突；NPU 旁的收益相对 23.89 s 可忽略。

## 4 顺带一个实测反常点（对我们自己更重要）

**同一批块，"4 块装一个 `.glc512`" 是 3.65 s/块，拆成 4 个单块容器只要 2.13 s/块**，即现有 512 组装路径有约 1.5 s/块的额外开销。这是 B 侧实现问题，不是你们的码流问题；我们正在定位，若压到 2.1 s/块，现有 4 块大图可从 14.60 s 降到约 9 s——**不增加码率、不改协议**。查到结论单独回一封。

## 5 我这边多做的两项实测（含一条对你们 §5 代码的修正建议）

### 5.1 现有 4 块输出的真实接缝梯度（B 板实测，比你们 PC 链的数更差）

**口径**（写清，便于你们复算）：对 512×512 RGB 输出，`gx = |diff(axis=1)|`、`gy = |diff(axis=0)|`；
竖缝比值 = `mean(gx[:,255,:])` / `mean(所有非 255 列的 gx)`，横缝同理取行 255。样本 = 板端 `pack/rxs` 里 13 张真实 512 解码 PNG。

| 统计 | 竖缝比值 | 横缝比值 |
|---|---|---|
| 平均（13 张） | **3.13** | **2.83** |
| 最差 | **5.76**（s499） | **4.45**（s492） |
| 最好 | 1.43（s500） | 1.39（s493） |

对照你们 A/021 §0 的 PC 链数（竖 1.71、横 1.49、最差 3.08）：**B 板输出比 PC 链更明显**。
所以"治缝"在板端的收益比 PC 上更大；这一条只描述现象，不代表我们已经做出融合修复。

### 5.2 平顶窗融合：用真实解码像素验证，发现你们 §5 片段最外 1 px 有数值问题

用上面 s500_big.png 的真实像素，按 §5 代码原样跑 9 窗融合（9 个窗都取自同一张真实解码图，所以理想误差应为 0）：

| 归一化下限 | 最大误差 | PSNR |
|---|---|---|
| `np.maximum(wt, 1e-6)`（A/021 §5 原文） | **209.15 LSB** | 49.47 dB |
| `1e-9` | 0.000 LSB | 150.05 dB |
| `1e-12` | 0.000 LSB | 150.05 dB |
| 权重加下限 `max(WY*WX, 1e-3)` | 0.000 LSB | 149.98 dB |

原因：`ramp=64` 时 `flat_top(256,64)[0] = 0.5-0.5·cos(π·0.5/64) ≈ 1.5e-4`，**角点 `Σw = 2.27e-8`**，
比 1e-6 的下限还小 ⇒ 除的是 1e-6 而不是真权重，角点被放大成 209 LSB（可见的亮点/亮边）。
**建议把 §5 的 `np.maximum(wt, 1e-6)` 改成 `1e-12`（或给权重本身加 1e-3 下限）**，其余不动。

融合耗时（真实 512 像素、numpy、板端）：**0.017–0.105 s**，与之前随机块的 0.081 s 同量级。

融合计时（CPU，与板上同一份 numpy）：

```python
import numpy as np, time
def flat_top(n=256, ramp=64):
    t = np.arange(n, dtype=np.float32); w = np.ones(n, np.float32)
    m = t < ramp;                w[m]  = 0.5 - 0.5*np.cos(np.pi*(t[m] + 0.5)/ramp)
    m2 = t >= n - ramp;          w[m2] = 0.5 - 0.5*np.cos(np.pi*(n - t[m2] - 0.5)/ramp)
    return w
WY, WX = flat_top()[:, None], flat_top()[None, :]
COORDS = [(0,0),(0,128),(0,256),(128,0),(128,128),(128,256),(256,0),(256,128),(256,256)]
p = [np.random.rand(256,256,3).astype(np.float32) for _ in range(9)]
t0 = time.monotonic()
out = np.zeros((512,512,3), np.float32); wt = np.zeros((512,512,1), np.float32)
for i,(y,x) in enumerate(COORDS):
    w = (WY*WX)[..., None]
    out[y:y+256, x:x+256] += p[i]*w
    wt [y:y+256, x:x+256] += w
out /= np.maximum(wt, 1e-6)
print('fusion %.3f s' % (time.monotonic()-t0))   # 板端实测 0.081 s
```
