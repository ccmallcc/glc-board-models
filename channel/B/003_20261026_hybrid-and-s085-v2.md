## 2. 关于你们 §3 的自洽性证明（口径收窄）

```
你们用 pc_decode_selfcontained.py 解自己产的 316 B，PNG md5 与编码端一致。
我们的判断：这只证明【同一运行时内，编码端与解码端自洽】，不能外推到跨运行时，更不能外推到我们 NPU。
（B/001 §2 已记：8/8 模型 md5 与你们 Release 相同 —— 那证明的是"同一份编译产物"，不是"跨运行时逐位一致"。）
我们的 62–65 dB 是另一侧证据：同一份产物、我们的运行时，先验算出来一致（否则会掉到 8~14 dB）。
其中"差异只剩 S4 的 fp32-vs-int8"是推算，未做实验分离。
```

## 3. 回答 §7.2：4 B 校验和，接受；两种方案都给实测值

```
容器：s085（md5 e9b07f13c65186fb461b377b5f024d28，292 B）
定义：idx_k = entropy_model.build_indexes( compact_masked(scales_k, mask_k).clamp_min(SCALE_MIN) )
drift：scales ← scales·(1+ε) + ε；means ← means + ε（ε 见下）
命令：python priors_checksum.py --glc s085_rx1.glc --drift <ε>
```

**16 B 方案（每段一个 CRC32）—— 实测**

```
stage0 0x0231B5B7   drift 0/1e-7/1e-5/1e-3 不变；1e-2 → 0x8A3D4962
stage1 0x73332C30   1e-3 → 0xF81F42FD
stage2 0xBFA49ADB   1e-3 起跨次运行不稳定（不给单点）
stage3 0x6C3EA915   1e-7 → 0xBD7B22D9（1e-5 同值）
```

**4 B 方案（四段 int32le 拼接后一个 CRC32）—— 只算出值，未做端到端验证**

```
drift 0：0xABDE9F19
```

```
结论：两种方案都能工作；4 B 省 12 字节且不影响 bpp，我们同意用 4 B。
但请你们注意：4 B 方案的"四段拼接"是我们提的，实测值只有一个（0xABDE9F19），还需要你们那边独立算一遍对上。
若你们更倾向每段独立可比对（便于定位是哪一段失步），那就得 16 B（对 292 B 容器 +5.48%）。取舍你们定，我们两种都能实现。
```

## 4. s085：数值归属分清（这是 v1 写错的地方）

**板端解码 PNG**（`md5 edbb04ea348c7beab18daa0ddc89ad36`，145,860 B，就是 A/003 §3 引的那张）：

```
PSNR 8.06 dB（对 IMG_0036.jpg；255 峰值、整幅 RGB、uint8）
每通道均值：原图 R76.1 G75.3 B57.7 → 板端 R237.1 G48.9 B56.1
R−G：原图 +0.8 → 板端 +188.2
每通道拟合（板端 = a×原图 + b，x = 原图对应通道）：R 0.6655x+186.41（饱和 57.2%，阈值=像素≥250）；G 1.5105x−64.81；B 1.1049x−7.65
```

**本机 int8 链解同一容器**（另一份 PNG）：

```
PSNR 8.068 dB；饱和 57.15%；拟合 R 0.6619x + 186.82
⇒ 与板端几乎一致（差异来自 S4 的 fp32-vs-int8 —— 此句为推算，未做实验分离），说明"红"不是某台机器的偶发问题
```

**五份重复**：s078 / s084 / s085 / s099 / s106 容器 md5 全为 `e9b07f13…`、各 292 B（板端 `md5sum` 分组 + 本地归档交叉验证）。

**关于它是哪一类**：

```
能支撑的：同一套 _ZG 在别处能到 62~65 dB，而 s085 只有 8 dB ⇒ 它不是用我们这套 _ZG 产的（实测支撑）。
不能支撑的："292 B 不在 308 / 312–324 区间"—— 312–324 是 verify-int8 里【四张别的图】的尺寸，
           不能用来排除"IMG_0036 的 int8 产物恰为 292 B"。这条我们撤回。
⇒ 结论改为【推算】：s085 由另一套先验产物（旧 compile 目录或已弃用配置）产生，需你们复现才能定死。
```
