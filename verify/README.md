# GLC2 解码一致性校验向量（fp32 参考实现）

```
IMG_0036.glc     308 B    容器
IMG_0036.jpg      21 KB   原图（256×256）
rec.png          118 KB   参考解码（PSNR 26.61 dB）
decode.py                 参考解码器（只吃 .glc，必须 CPU）
verify.py                 比对你的解码（零依赖）
MANIFEST.md               全部 md5 与复现记录
```

---

## 为什么这一版要重做

2026-10-24 发布的那份 308 B 容器是在 **CUDA** 上编的。实测（2026-10-25）：

| 容器产自 | 解码设备 | 结果 |
|---|---|---|
| CUDA（10-24 那份） | CUDA 新进程 | **NaN** |
| CUDA | CPU | 12.84 dB |
| **CPU（本版）** | **CPU 新进程** | **26.61 dB** ✅ |
| CPU（本版） | CPU 单线程 | 26.61 dB，**PNG md5 完全相同** |
| CPU（本版） | CUDA | NaN |

**根因：cuDNN 的算法自动选择不是跨进程确定的**，所以 CUDA 产的容器连 CUDA
自己新开进程都解不开。CPU 路径相反 —— 跨进程、跨线程数都逐位一致。

所以本版在 **CPU** 上重编。画质不变：新 `rec.png` 与旧的那张**最大只差 1 个灰度**
（PSNR 64.14 dB），对原图仍是 **26.61 dB**。所有已发布的对比图、材料数字都不用动。

## 怎么验

### 第一档：只看图对不对（零依赖，不需要模型）

```bash
python verify.py 你的解码.png
```

和 `rec.png` 比 PSNR：**≥40 dB** 逐像素一致；**32–40 dB** 先验对上了但 S4 不同；
**<32 dB** 解错了。实测失步时落在 **12–15 dB**，完全解不开是 NaN。

### 第二档：从容器自己解一遍（要模型）

```bash
python decode.py IMG_0036.glc --img IMG_0036.jpg --out my_rec.png
```

结果应与 `rec.png` **逐字节相同**，PSNR 26.61 dB。

**必须 CPU。** `decode.py --device cuda` 会直接报错退出。

## 这个向量证明什么

1. **容器是自包含的**：只给 308 B，不给任何 scales/means 旁路数据，就能解出图。
2. **解码是可复现的**：换进程、换线程数，结果逐字节相同。
3. **公开的画质数字是真的**：26.61 dB 可以自己算出来。

## 不证明什么

1. **不证明跨计算后端可解。** 同一份容器在 CUDA 上解是 NaN。`GLC2` 不存先验，
   解码端必须重算，而 cuDNN 不是跨进程确定的 —— 这是格式的边界，不是实现 bug。
2. **不证明板端 int8 链能解。** 板端是 INT8 `_ZG` 子图，与 fp32 参考实现不是同一套先验。
   板端那套要另一组向量（int8 产出、int8 解出，平均 21.60 dB）。
3. **只跑了 1 张图、只跑 `q=0`。**

---

## 一句话

**容器绑定计算后端。CPU 是确定的，CUDA 不是。** 本向量在 CPU 上产出，
也必须用 CPU 解 —— 这条不是限制，是 `GLC2` 格式的物理事实。
