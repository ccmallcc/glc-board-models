## 二、解码一致性校验向量（INT8 链）

`verify/` 里 15 个文件：

| 文件 | 是什么 |
|---|---|
| `glc/full_img{0..3}.glc`（312–324 B） | **板端 INT8 `_ZG` 链**产出的容器 |
| `src/full_img{0..3}.png` | 编码器的输入（256×256，Kodak24 crop） |
| `rec/full_img{0..3}.png` | **参考解码**（同一套 INT8 `_ZG` 子图解出来的） |
| `check.py` | Tier 1：查指纹 + 重算 PSNR（零依赖） |
| `verify.py` | Tier 3：比对你的解码输出 |
| `MANIFEST.md` | 全部 md5、期望值、复现记录 |

### 为什么必须是 INT8

`GLC2` 容器**不存 scales/means**，只存 z 的 16 个索引（28 B）。
解码端必须自己从 `z_hat` 把每个相位的熵参数重推出来，**且必须逐位一致**——
rANS 是顺序状态机，第 i 个符号的 CDF 错一格，后面整段就废。

板端编码用的是 **INT8 `_ZG`**。所以：

- 用**同一套 INT8 `_ZG`** 解 → 逐位一致，能解；
- 用 **fp32 PyTorch 参考实现**去解 int8 容器 → 推出来的不是同一套参数 → **全 NaN 或整段崩**。

这不是实现 bug，是格式本身的约束：**容器只能被与它同源的先验路径解开。**
我们把"同源"落在 INT8 上，因为那是板的实际运行形态，也是整数运算、天然可跨实现复现的那一侧。

### 参考值（实测）

| 样本 | 容器 | bpp | PSNR（源图 vs 参考解码） |
|---|---:|---:|---:|
| 0 | 324 B | 0.03955 | **18.19 dB** |
| 1 | 316 B | 0.03857 | **22.99 dB** |
| 2 | 316 B | 0.03857 | **19.79 dB** |

口径：256×256、`q=0`。

### 三档怎么验

**Tier 1 —— 零依赖，任何人有 Python 就能跑**

```bash
cd verify && python check.py
```

校验 12 个文件的 md5，再用源图与参考解码重算 PSNR，应得上面那张表。
这一档证明**你拿到的是同一份文件、公开数字是真的**，但**不解码容器**。

**Tier 2 —— 需要模型 + Icraft 运行时**

```bash
python3 "AB板/02_A侧代码/07_解码端/工具/pc_decode_selfcontained.py" \
        --glc_dir verify/glc --png_dir verify/src --n 4 --device cuda
```

**只喂 `.glc`**，不喂任何 scales/means 旁路数据。解出来的 `_rec.png` 应与仓库里的
**逐字节相同**。这一档才证明**容器本身是可独立解码的**。

**Tier 3 —— 你自己的解码器**

```bash
python verify.py 你们的输出.png          # 自动挑最接近的样本
python verify.py 你们的输出.png 2        # 指定样本
```

判据是与 `_rec.png` 的 PSNR：**≥ 40 dB** 逐像素一致；**32–40 dB** 有差异但结构对
（通常是 S4 生成器实现不同）；**< 32 dB** 解错了。

参考尺度：解错一个相位是 ~13–15 dB，完全解不开是 NaN。32 dB 这条线离两边都很远。

### 如果 FAIL 怎么定位

按这个顺序查，前一条不过后面都白搭：

| # | 查什么 |
|---|---|
| 1 | 容器 md5 —— 跑 `check.py` |
| 2 | 模型 md5 —— 见上面的表，8 个数必须逐个对上（尤其别用 `compile2` 那套） |
| 3 | 解码是不是**同一套 int8 子图**？fp32 PyTorch 解 int8 容器必然崩 |
| 4 | 胶水的 1×1 卷积（768→256）必须 **float64 累加**再转 float32；末位差会被 S3 的 int8 量化边界放大成符号翻转 |
| 5 | HostRunner 入参是 **NCHW**（内部自己转 NHWC）；转置两次会得到"36%~42% 元素恰好相同"的假象 |

### 旧向量（`IMG_0036.glc`）已撤回

那 308 B 是 **fp32 参考链**产出的。同一个进程里编、同一个进程里解是 26.61 dB，
**换一个进程解就是 14.60 dB**（实测 2026-10-25）——容器里没有先验，
而 fp32 侧的先验重算不可跨进程复现。

那组文件已删除。`rec.png` 本身没错，错的是"它可被独立复现"这个说法。

## 三、容器格式（自查用）

```
76 B 头： "GLC2" | ver(2) | 0,0 | 10×u32 | z_count | z_pay_len | 4×u32 流长度 | pad
后面是 4 条流，长度就是头里那 4 个 u32
```

**头里没有分辨率、没有原始大小**——`256×256` 还是 `512×512` 由协议 `SESSION_BEGIN.MODE`
决定（0=小图 256×256；1=大图 4 帧拼 512×512，顺序顺时针 TL,TR,BR,BL）。

A 侧完整对接说明见我们私下的 `92_给B_对接说明`，需要的话找我们要一份。

## 四、常见问题

**Q：为什么不直接放进 git？**
A：单个 `.raw` 150 MB，超过 GitHub 单文件 100 MB 硬限制；走 Git LFS 会消耗带宽配额。
放 Release 资产（单文件上限 2 GiB）既不受限、下载也不算 LFS 配额。

**Q：模型能在 PC 上用吗？**
A：能用，但要 Icraft 运行时（`icraft-run.exe`，HostBackend 后端）。
PC 上的 PyTorch 参考权重 `GLC_image.pth.tar`（667 MB）是**另一条链路**，
和这套 `_ZG` 不通用——混着用就是上面说的"整段崩"。

**Q：我们只需要解码，需要全部 10 个文件吗？**
A：**解码只要 8 个**：`s2` + `s3_phase1/2/3` 的 json+raw。`s1` 只在编码侧用。
但既然 md5 表在，建议全下，缺哪个一眼能看出来。

**Q：为什么 PSNR 只有 21.60，你们材料里写的不是这个数？**
A：材料里 21.80 是"旧 PC fp32 链"，21.73 是"板端容器 + 编码端导出旁路参数解"，
21.60 是"板端容器 + 解码侧自算参数解"。**只有 21.60 这条是完全自洽的**，
也是本向量采用的口径。三者差 0.2 dB，都属同一批图。

**Q：Tier 2 跑出来报 `拿到 0 个 v_id`？**
A：多半是 WSL 的 Windows interop 掉了，`icraft-run.exe` 其实报了
`Exec format error` 但 stdout 被解码器吞掉了。跑一次 `wsl --shutdown` 让它自己
重新注册 binfmt 即可（**别手工注册** `:WSLInterop:`）。这个坑 2026-10-25 一天内出现过两次。
