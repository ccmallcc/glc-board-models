## 二、解码一致性校验（建议**先做这个**）

`verify/` 里三个文件：

| 文件 | 是什么 |
|---|---|
| `IMG_0036.glc`（308 B） | 用 A 侧参考实现（PyTorch）编出来的**合法容器** |
| `rec.png`（118 KB） | 同一个参考实现解出来的**正确结果** |
| `IMG_0036.jpg`（21 KB） | 原图（256×256） |

### 验收流程

1. 用**你们的解码器**解 `IMG_0036.glc` → 存成 PNG（256×256）
2. 跑 `verify.py` 把它和 `rec.png` 比：

```bash
python verify.py 你们的输出.png
```

3. 输出会直接告诉你 **PASS / FAIL**，以及是"偏色"还是"结构不对"。

### 参考值（A 侧 PC 实测）

```
容器 308 B   PSNR 26.61 dB
每通道均值：输入 R76.1 G75.3 B57.7  →  解码 R74.0 G74.1 B55.8
偏色指标 R−G：输入 +0.8 → 解码 −0.1
```

**PASS 判据**（`verify.py` 里有）：PSNR ≥ 24 dB 且每通道均值差 ≤ 6 且 R−G ≤ 20。

### 如果不 PASS 怎么定位

`verify.py` 会把每通道的 `a`、`b` 拟合出来（模型 `y = a·x + b`）：

| 现象 | 大概率原因 |
|---|---|
| 三个通道的 `a`/`b` 差很多、某个通道大量饱和 | **反归一化常数**（每通道 mean/std）用错 |
| R 整体被抬高（例如 `b ≈ +190`）、G 被压缩 | **YCoCg / YUV → RGB** 的矩阵或偏移写错 |
| 某个通道大面积 250 以上 | **int8 反量化的 scale / zero-point** 用错 |
| 结构都对、只是整体亮一点暗一点 | 正常量化误差，可接受 |

> 真实案例：2026-10-23 我们收到一张解出来**整体发红**的图（R 均值 230、27% 像素饱和、
> R−G = +179.7），而同一容器用参考实现解出来是 R−G = −0.1。用上面这张表就能定位到
> "每通道仿射常数不一致"，不是传输、不是通道顺序、也不是分块拼接。

## 三、容器格式（自查用）

```
76 B 头： "GLC2" | ver(2) | 0,0 | 10×u32 | z_count | z_pay_len | 4×u32 流长度 | pad
后面是 4 条流，长度就是头里那 4 个 u32
```

**头里没有分辨率、没有原始大小**——`256×256` 还是 `512×512` 由协议 `SESSION_BEGIN.MODE`
决定（0=小图 256×256；1=大图 4 帧拼 512×512，顺序顺时针 TL,TR,BR,BL）。

A 侧完整对接说明见我们私下的 `92_给B_对接说明`，需要的话找我们要一份。

## 四、常见问题

**Q：为什么不直接放进 git？**
A：单个 `.raw` 150 MB，超过 GitHub 单文件 100 MB 硬限制；走 Git LFS 会消耗带宽配额。
放 Release 资产（单文件上限 2 GiB）既不受限、下载也不算 LFS 配额。

**Q：模型能在 PC 上用吗？**
A：不能。这些是 **ZG330/icraft 量化格式**（`*_ZG.json` 描述 + `.raw` 权重）。
PC 上的 PyTorch 参考权重是另一份 `GLC_image.pth.tar`（667 MB），两者不通用。

**Q：我们只需要解码，需要全部 10 个文件吗？**
A：解码路径用到 s2（hyperdec）+ s3（三个阶段）+ s1 里的部分；稳妥起见**全下**，
反正 md5 表在，缺哪个一眼能看出来。
