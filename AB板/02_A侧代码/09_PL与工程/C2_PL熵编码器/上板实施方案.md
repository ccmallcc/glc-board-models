## 二、⭐⭐ PL 时钟管脚 —— **找到了**

### 2.1 官方 XDC 原文

`fpai_demo_fpga/constrs_1/impl_constraints.xdc`：

```tcl
create_clock -period 5.000 [get_ports sys_clk_p]
set_property IOSTANDARD DIFF_SSTL15 [get_ports sys_clk_p]
set_property IOSTANDARD DIFF_SSTL15 [get_ports sys_clk_n]
set_property PACKAGE_PIN C8 [get_ports sys_clk_p]
set_property PACKAGE_PIN C7 [get_ports sys_clk_n]
```

### 2.2 三条独立证据一致

| 证据 | 内容 |
|---|---|
| **官方 XDC** | `sys_clk_p/n = C8/C7`，`DIFF_SSTL15`，`create_clock -period 5.000` = **200 MHz** |
| **Lite 手册特性表** | 「时钟管理 \| **PS侧50MHz、PL侧200MHz**」 |
| **Xilinx 官方封装表** | `C8 = IO_L13P_T2_MRCC_34`、`C7 = IO_L13N_T2_MRCC_34` —— **Bank 34 的 MRCC 差分时钟对** ✅ |

**而且这份 XDC 的其它管脚与我们已核实的完全一致**，可以互证：

| 信号 | XDC | 我们此前已知 |
|---|---|---|
| `sys_rst` | **F8** | `PL_KEY1 = F8 = IO_L11P_T1_SRCC_34` ✅ |
| `rx_gtx_full_reset` | **E7** | `PL_KEY2 = E7` ✅ |
| `led[0]` / `led[1]` | **J1 / M6** | `PL_LED1 = J1`、`PL_LED2 = M6` ✅ |

⇒ **`C8/C7`（Bank 34，MRCC 差分，200 MHz）就是我们的 PL 系统时钟输入。**

> ⚠️ **一个残留不一致，要留意**：Lite 手册 §时钟管理 的**正文**列的是
> 「固定频率 50MHz 的晶振、固定频率 100MHz 的晶振、DDR 的外部 200MHz 时钟等」，
> 与特性表的"PL侧200MHz"**表述不同**。

### 2.2.1 ✅ 这个不一致已闭环 —— 官方 RTL 里它就叫 `sys_clk_200m`

`rtl/ai7030_edif_top.v` 顶层端口：

```verilog
input  sys_clk_p ,      // line 55
input  sys_clk_n ,      // line 56
...
.sys_clk_p     ( sys_clk_p ),
.sys_clk_n     ( sys_clk_n ),
.sys_clk_200m  ( hp_clk    ),   // ⭐ line 224 —— 内部信号名直接叫 sys_clk_200m
```

⇒ **四个证据闭环**：

| # | 证据 | 内容 |
|---|---|---|
| 1 | 官方 XDC | `sys_clk_p/n = C8/C7`，`period 5.000` |
| 2 | **官方 RTL 内部信号名** | **`sys_clk_200m`** ⭐ |
| 3 | Lite 手册特性表 | 「PL侧 **200MHz**」 |
| 4 | Xilinx 封装表 | `C8/C7 = IO_L13P/N_T2_MRCC_34`（Bank 34 MRCC 差分对） |

**`C8/C7` = 200 MHz 差分 PL 系统时钟，无歧义。**（手册正文那份晶振清单说的是板上晶振，
200MHz 应来自时钟芯片而非晶振 —— 但这不影响管脚与频率的结论。）

### 2.2.2 ⭐ 板型设置：**官方交付的 XDC 已经配好 Lite 了，不用改**

`FPAI_DEMO说明.pdf` §二 要求「根据使用的开发板型号，修改 `impl_constraints.xdc` 的管脚约束」：

```tcl
(1) 悟净开发板      → U6 / U5
(2) 悟净开发板 Lite → R6 / R5     ← ✅ 我们
```

**但 rar 里那份文件已经是 Lite 配置了**（`impl_constraints.xdc` 第 31~34 行原文）：

```tcl
create_clock -period 6.734 [get_ports FMC_HPC_GBTCLK0_M2C_C_P]
##set_property PACKAGE_PIN U6 [get_ports FMC_HPC_GBTCLK0_M2C_C_P]  ## WUJING BOARD
##set_property PACKAGE_PIN U5 [get_ports FMC_HPC_GBTCLK0_M2C_C_N]
set_property PACKAGE_PIN R6 [get_ports FMC_HPC_GBTCLK0_M2C_C_P] ## WUJING LITE BOARD
set_property PACKAGE_PIN R5 [get_ports FMC_HPC_GBTCLK0_M2C_C_N]
```

⇒ **U6/U5 已被注释掉，R6/R5 生效 —— 正好是 Lite。所以这一步不用做**，
只要**别手滑把注释反过来**。（这也是一个额外的旁证：这份工程交付时就是给 Lite 用的。）

> ⚠️ 注意这只影响 **GT 参考时钟**（`FMC_HPC_GBTCLK0_M2C_C`），**不影响 `sys_clk`（C8/C7）**。
> 我们**不用 GT**（不跑 PCIe/SFP/SDI），所以这条即使配错也不致命 —— 但配对了更省心。

### 2.3 顺带解决的另一件事

`impl_constraints.xdc` 里还给了 **HDMI 输出**管脚（我们做脱机演示要用）：

⚠️ **板型差异**（官方文档明说，改错就上不了板）：

set_property PACKAGE_PIN U5 [get_ports FMC_HPC_GBTCLK0_M2C_C_N]

## 三、⭐⭐ 自定义算子的官方接口（照抄即可）

`FPAI_DEMO说明.pdf` §四/§五 + `rtl/adder_op/adder_top.v`。

### 3.1 两路接口

| 接口 | 谁当 master | 干什么 |
|---|---|---|
| **寄存器访问端口** | **PS 是 master** | PS 读写 PL custom op 的寄存器（配置地址/长度/启动/查状态） |
| **数据访问端口** | **PL custom op 是 master** | custom op 自己读写 **PL DDR**（拿输入、写输出） |

### 3.2 RTL 信号（官方表格）

**寄存器端口**（`ra_` 前缀，类 AXI-Lite）：

| 信号 | 位宽 | 方向 |
|---|---|---|
| `itf_ra_awaddr` / `itf_ra_awdata` / `itf_ra_awvalid` | 32 / 32 / 1 | 输入 |
| `itf_ra_awready` | 1 | 输出 |
| `itf_ra_araddr` / `itf_ra_arvalid` | 32 / 1 | 输入 |
| `itf_ra_arready` | 1 | 输出 |
| `itf_ra_rdata` / `itf_ra_rvalid` | 32 / 1 | 输出 |
| `itf_ra_rready` | 1 | 输入 |

**数据端口**（`itf_` 前缀）：

| 信号 | 位宽 | 方向 |
|---|---|---|
| `itf_awaddr` | 32 | 输出 |
| `itf_awdata` | **64**（官方 `adder_top` 用）／**512**（PDF 表格写） | 输出 |
| `itf_awvalid` / `itf_awready` | 1 | 出／入 |
| `itf_araddr` / `itf_arvalid` / `itf_arready` | 32 / 1 / 1 | 出／出／入 |
| `itf_rdata` / `itf_rvalid` / `itf_rready` | **64**／1／1 | 入／入／出 |

⚠️ **位宽有一处不一致**：PDF 表格写 `User_Ddr_*data` 是 **512 位**，而官方 `adder_top.v` 里是 **64 位**。
**以能编译的 `adder_top.v` 为准**（64 位），512 位可能属于另一个版本或大缓冲配置。
**开工前先用 `adder_top.v` 跑通**，再按需要加宽。

**字节使能**：PDF 说 `User_Ddr_awwinfo[70:7]` 是写字节使能（每 bit 对应 data 的一个字节）——但
`adder_top.v` 里**没有 awwinfo 端口**。同样以 `adder_top.v` 为准。

### 3.3 官方模板的结构 —— **我们只要换掉中间那一块**

`adder_top.v` 的分工：

```
        ┌──────────────────────────────────────────────┐
itf_ra_*│  reg_ctrl   ── 寄存器解析 / 起始 / 完成 / 基址  │
        │      │ comp_start / comp_done                  │
        │      │ arbase,arsize (读) / awbase,awsize (写)  │
        │      ▼                                        │
        │   dma  ── PL DDR 读 ──► 计算核 ──► PL DDR 写     │
        │      │                    │                    │
        │      │              ★ 把 adder 换成 rans ★      │
        │      ▼                                        │
        │  pulse_cross ×2 ── clk ↔ ra_clk 跨时钟域脉冲     │
        └──────────────────────────────────────────────┘
```

**计算核（`adder`）的流接口 —— 这就是 rANS 要实现的**：

```verilog
module rans (
    input  [63:0] a,          // 输入流：符号 + scale
    input         a_valid,
    output        a_ready,
    output [63:0] sum,        // 输出流：码流
    output        sum_valid,
    input         sum_ready,
    input  [15:0] arsize,     // 数据量
    output        comp_done,  // 完成标志
    input         clk, rst_n
);
```

**寄存器**：除 `reg_ctrl` 自带的启动/完成/读写基址长度外，官方还留了
**`rfu_rreg0~9` / `rfu_wreg0~9` 共 10 个读 + 10 个写备用寄存器**给用户 ——
我们可以用它们传 rANS 需要的参数（比如 q 值、阶段号）。

### 3.4 PS 侧驱动（C++ API）

```cpp
// custom op 寄存器地址空间 = 0x400C'0000 ~ 0x400F'FFFF
int  v = device.defaultRegRegion().read (addr, /*relative=*/false);
     device.defaultRegRegion().write(addr, value, false);

// 分配 PL DDR
auto mem = device.defaultMemRegion().malloc(byte_size, /*auto_free=*/false, /*align=*/64);
mem.write(dest_offset, src, byte_size);
mem.read (dest, src_offset, byte_size);
```

⚠️ **与我们此前的记录冲突，要核对**：`自定义硬算子官方机制调研报告.md` 记的是
**GP1 `0x800C_0000 ~ 0xBFFF_FFFF`**，而本 PDF 写 **`0x400C'0000 ~ 0x400F'FFFF`**。
两者可能分别是 **PL 侧视角**与 **PS 地址映射**。**开工时以官方 demo 的实测地址为准。**

### 4.3 上板：**两条路，开发期走「热加载」，交付走 BOOT.bin**

#### 4.3.A ⭐ 开发期主路径 —— **`fpga_manager` 热加载（不重启、不烧卡、不用 JTAG）**

**2026-09-22 在板上实测通过。** 板端 Linux 已经编好了复旦微自己的 FPGA manager：

```
CONFIG_FPGA=y
CONFIG_FPGA_MGR_FMQL_FPGA=y     ← 复旦微自己的驱动
CONFIG_FPGA_BRIDGE=y
CONFIG_FPGA_REGION=y
CONFIG_OF_FPGA_REGION=y
```
```
/sys/class/fpga_manager/fpga0 -> .../e0040000.devcfg/fpga_manager/fpga0
  name  = FMSH FMQL FPGA Manager
  state = operating
dmesg: fpga_manager fpga0: FMSH FMQL FPGA Manager registered
```

**一步到位（PC 侧，一条命令）**：
```powershell
python 工具\hotload_bitstream.py --bit <Vivado产的>.bit --board 192.168.1.2 --smoke
```
它内部做三件事：`.bit → .bin` → `scp` 到板子 `/lib/firmware/` → 写
`/sys/class/fpga_manager/fpga0/firmware` 触发重配。`--smoke` 会顺便跑一次 S1 推理做验证。

**板上手工做**：
```bash
cp <name>.bin /lib/firmware/
bash 工具/板端脚本/hotload_bitstream.sh <name>.bin
```

**`bit → bin` 的转换规则（已逐字节验证）**：
> `.bin` = **去掉 `.bit` 的头部** + **按 32 位字做字节反序**
>
> 板上 `ai7030_top_disable_icap.bit` 头长 **144 字节**；用
> `工具/bit_to_bin.py` 转换后与板上原厂 `/lib/firmware/ai7030_top_disable_icap.bin`
> **5,980,460 字节逐字节完全相同（0 处不同）**。
>
> `.bit` 头结构（顺带把设计信息也读出来了）：
> ```
> magic 13B  00 09 0F F0 0F F0 0F F0 0F F0 00 00 01
> 'a' + u16 设计名  = ai7030_top;UserID=53180205;Version=2018.3;Patched=DISABLE_ICAP,VCCM;PatchID=32494
> 'b' + u16 器件名  = 7z030ffg676
> 'c' + u16 日期    = 2026/05/29
> 'd' + u16 时间    = 10:10:49
> 'e' + u32 数据长度 + 位流数据
> ```
> ⭐ **头里自己写着 `Patched=DISABLE_ICAP,VCCM;PatchID=32494`** ——
> 这是官方位流确实打过 IP_PATCH 的直接证据，也印证了 `_disable_icap` 后缀的含义。

**实测记录（累计 4 次加载，全部返回 0）**：

| # | 时刻(dmesg) | state | 加载后 S1 `total_hard_time` |
|---|---|---|---|
| 1 | `1412.622820` | operating | — |
| 2 | `1415.076803` | operating | — |
| 3 | `1675.593284` | operating | **346.731 ms** |
| 4 | `1700.977528` | operating | — |

> **对照 V16 无热加载时的 `total_hard_time = 346.753 ms`** ⇒
> 热加载后 PL **仍然是活的、且数字逐位一致**（差 0.008~0.022 ms，属抖动）。

⇒ **开发循环变成：Vivado 出位流 → scp → 写 sysfs → 重跑板端程序。全程约数秒，无需重启。**
> ⚠️ 热加载是**整体重配**：正在跑的板端程序会失去 PL，**必须重跑**。

#### 4.3.B 交付/固化路径 —— 换 `BOOT.bin`（官方两条路）

1. 改 `BOOT_Gen/7030ai_psin.bif` 里的路径（不要反斜杠）
2. 把 Vivado 产的 `.bit` 拷进 `BOOT_Gen`，**文件名要与 bif 里一致**
3. Procise → **Create Image** → 得 `BOOT.bin`
4. 替换 `BOOT.bin`：
   - **读卡器**：直接换 FAT 分区里的 `BOOT.bin`（**不要格式化**）
   - **SSH**：`mount /dev/mmcblk0p1 /root/bits` → 替换 → `reboot`
     ⚠️ **必须先挂载**，直接拷到 `/root/bits` **不生效**

> **板子实际情况（2026-09-22 实测，与官方教程有出入）**：
> - 启动分区 **`/dev/mmcblk0p1`（1 GB, W95 FAT16）默认不挂载**，且**板上没有 `/root/bits` 这个目录**
>   ⇒ 官方说的"若已挂载至 `/root/bits`"在我们板子上**不成立**，得先
>   `mkdir -p /root/bits && mount /dev/mmcblk0p1 /root/bits`。
> - `/etc/fstab` 里**没有** `mmcblk0p1`，所以每次重启都要重新挂。
> - 分区表：`p1 = 1G FAT16`、`p2 = 26.1G Linux`（`/`，ext4）。
> - **启动分区的完整清单**（已备份到 PC，见下）：
>   `BOOT.bin`、`BOOT_npu_2025.bak`、`FSBL251210_ddr400_demo.out`、`Image`、
>   `ai7030_top.bit`、`ai7030_top_disable_icap.bit`、`bl31.elf`、`fmqlmp-verify.dtb`、
>   `u-boot`、`uEnv.txt`。
> - ⭐ **原厂备份已经做了**：`E:\fudanwei\_board_backup\bootfat_20260922\`
>   （md5 与板上逐一核对一致：`BOOT.bin = 416d7b6f875b78b8ac7cbad0cecb3085`、
>   `BOOT_npu_2025.bak = 897c462ff5d16b9cdc537bf8574839a7`、
>   `ai7030_top.bit = b1cf2f228975e7397e69dff3cbd8ed7c`、
>   `ai7030_top_disable_icap.bit = 24e86606829a49e98f9abb7355a0c633`）。

> ### ⭐ 不需要调试器（官方原文）
>
> 《30TAI使用教程》§3.3「替换BOOT.bin」**只给两条路**：**读卡器** 与 **SSH**。
> 后者原文：「通过SSH远程连接开发板（登录账户需为root）……完成替换后，执行reboot命令重启开发板。
> **重启系统后位流生效**。」
> ⇒ **"用网口把位流写进 SD 卡"就是官方主路径**，一条网线即可，**全程不碰 JTAG**。
>
> **机制**：`BOOT.bin` = FSBL + **我们的 `.bit`** + `bl31.elf` + `u-boot`，
> 由 FSBL 在**每次上电**时从 SD 卡 FAT 分区读出、经 **PCAP** 推进 PL。
> 板上有 JTAG（Lite：`1路PS_JTAG、1路PL_JTAG`），但那只服务于 **QSPI 固化**与 **ILA 在线调试**。
>
> **唯一真正的风险**：**换坏了 `BOOT.bin` 板子就起不来**，恢复靠 **microSD 读卡器**
> （把卡拔下来在 PC 上还原），**不靠 JTAG** ⇒ 所以备份必须有（上面已经做了）。
> 开发期用 4.3.A 的热加载就完全不碰 `BOOT.bin`，这个风险等于零。

> ### ⚠️ 更正（本条 20 分钟前写错，就地改）：`disable_icap` **不挡** `fpga_manager`
>
> 先前这里写「**ICAP 路线堵死 ⇒ PL 换配置只能走上电加载**」。**结论下早了。**
>
> 事实分两层，要拆开看：
> ① 【官方手册，《Platform Tools 使用手册》L588-592】bitgen 补丁 **`disable_icap`
>    适用 `PSOC10、PSOC30、PSOC45、PSOC45AIX、PSOC45AIH`**，语义是「清除 icap 的配置位」，
>    且**与 `master_combine_Tandem` 补丁互斥**。
>    ⇒ 这挡掉的是 **ICAP**（用户逻辑里那个配置端口）做 IPROG/DFX 切换。
> ② 【实测，2026-09-22】`fpga_manager` 走的是 **PCAP**（`e0040000.devcfg`），**不是 ICAP**，
>    所以**不受 ① 影响** —— 上面 4 次热加载全部成功、PL 功能完好。
>
> **教训**：**"文档里说某条路不通"≠"没有别的路"**。
> 这一条我差点把"可用的开发主路径"写成"不存在"，只因为查了手册没去板子上 `ls /sys/class/fpga_manager`。
> 已登记为 `08` **坑 36**。


### 4.4 PL 侧的 NPU 是什么形态（重要）

- **`rtl/edif/AI_Mate.edif`** = NPU（诸葛）在 PL 里的实现，**以 EDIF 网表交付** ——
  所以我们**不能改 NPU 本身**，只能在它旁边挂 custom op。
- **`rtl/edif/AI_Mate_no_detpost.edif`** = **不含 DetPost 硬算子**的版本，
  官方明说「**可降低 PL 逻辑资源占用率**」。
  ✅ **我们不需要 DetPost**（那是检测后处理）→ **应该用 `no_detpost` 这个**。
- `rtl/gp/`（`gp0_manager.sv`、`gp_io.sv`、`mna_gp2axi.sv`…）与 `rtl/AI_Mate_stub.v`
  是 **PL ↔ NPU 的接口封装**（GP 端口 ↔ AXI）。

### 5.1 做 PL 到底值不值？—— 用实测数说话

| | 每符号 | @65,536 符号（256×256） |
|---|---|---|
| **板 A53 实测**（`V16`） | **549 ns** | **36 ms** |
| C2a1（逐位除法） | 660 ns | 43.3 ms（**比 A53 还慢**） |
| **C2c1（倒数乘法，端到端）** | **50 ns** | **3.28 ms** |

⇒ **PL 版比 A53 快约 11×**，但**省下的绝对时间是 33 ms**（占 V16 那 ~850 ms 全链路的 **4%**）。

> ⚠️ **所以"PL 做 rANS"的理由不能是"它是瓶颈"** ——
> 它**不是**瓶颈（NPU 354.87 ms + PC S4 445 ms 才是）。
> **真正的理由有三条**（`V18` §2.3 / `11`）：
> 1. **算术编码天生不适合 GPU/CPU**：实测 PC GPU 跑熵编码比 PC CPU **慢 20~26%** ——
>    它要的不是并行度，是**专用数据通路**，这是"该用硬件做"的直接证据；
> 2. **赛题硬性要求 ≥1 项 FPGA 开发**，本来就必须做；
> 3. 做进 PL 能**把 A53 从熵编码里彻底解放**（现在 36 ms/帧全压在 CPU 上），
>    这正是"PS + PL 协同"的叙事。
