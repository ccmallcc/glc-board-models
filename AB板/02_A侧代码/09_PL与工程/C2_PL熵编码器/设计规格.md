## 一、为什么做它、为什么不现在下结论

### 1.0 ⚠️ 先澄清一个最容易搞混的问题：**编码器到底给 CPU 还是给 PL？**

**答案：两个都要，而且不是二选一——它们是同一件事的两半。**

| | PS / CPU 版 | PL 版（本目录 = C2） |
|---|---|---|
| **在哪** | A53 上 | FPGA 逻辑里 |
| **是什么** | `assets\板端代码\glc_board_encoder.h`：rANS64 + 紧凑表查表 + escape/bypass + 定长打包 | 同一算法的硬件等价物 |
| **状态** | ✅ **已有，且与 compressai 逐字节对拍一致** | 🔵 **规格已定，RTL 起步**（仅仿真） |
| **角色** | **现在真正在板端跑的编码器**；同时是 **E3 对比实验里"软件实现"那一半** | 赛题硬性要求的那 **≥1 项 FPGA 开发** |

**为什么不能只做一个：**

1. **赛题硬性要求**「至少完成 1 项 FPGA 相关开发（…硬件加速 IP…）」→ **只有 PS 版不满足**（`11` §三原文）。
2. `11_官方赛题原文与评分标准.md:298` 原文：**「PL range coder vs PS range coder 的实测对比是必交作业，不是可选项」**
   → 这正是 **E3**（"应给出软件实现与 FPGA 实现的性能对比"）。**没有 PS 版就没有对照组。**
3. `02_硬件扫盲_NPU_CPU_FPGA.md:102` 把算术熵编码标注为 **「CPU 或 PL」**：
   *位级、逐符号串行；CPU 能做但慢，PL 做电路最合适。*

> 📌 **所以 PS 版不是"过渡方案"，它是基线 + 对照组的另一半。删掉它，E3 就没法做。**

**但"PL 到底做不做 rANS"仍未拍板** —— 见 §一 下表。

### 1.1 本规格的定位

| 项 | 说明 |
|---|---|
| **赛题硬性要求** | **≥1 项 FPGA 开发** + 端到端闭环。PL 侧熵编码是本队最自然的 FPGA 模块 |
| **⚠️ 前提未定** | `06` §三 C1：**「PL 到底做哪个模块」由板上实测 W1/W2 拍板**——AE 是瓶颈才做 rANS。目前外推 AE(**73~146 ms @256×256**，即 65,536 符号) 与 NPU 同量级 → **大概率该做** |
| **本规格的定位** | 是**技术可行性论证 + 设计基线**，不是"已经决定写进作品简介"。**写进简介 = 承诺 2~4 周 RTL**，那是团队要拍板的事 |
| **PL 时钟管脚缺失** | 位流**出不来** → 本模块**只能仿真验证**，上板要等 T10（FAE 给管脚表） |

> ⚠️ **替代方案的措辞要更正一处**：`06:83` 写的备选是「**PL 侧码流打包 + 以太网输出**」。
> 但 **lite 版 PL 端千兆网未焊接**（`11` §二 13 项未焊接第 ① 项），
> 所以**"以太网输出"在 lite 上不成立**，只剩「**PL 侧码流打包**」——数据仍要经 **PS 侧网口**发出。

## 二、算法基线（照抄 C++，不许重新推导）

```
scale(f32) --glc_build_index--> 行号 k --紧凑表--> (start, freq) --rANS--> 码流
```

| 常量 | 值 | 出处 |
|---|---|---|
| `RANS64_L`（state 初值） | `1 << 31` = `0x80000000` | `glc_board_encoder.h:27` |
| `GLC_PRECISION`（符号编码用） | **16** | `:28` |
| `GLC_BYPASS_PRECISION`（escape 用） | **4**，`MAX_BYPASS_VAL` = 15 | `:29-30` |
| 符号数 | 393,216 / 帧（768×512 的 y 通道） | `07_数字口径表.md` |

**每符号的核心更新**（`Rans64EncPut`，`:34-43`）：

```
x_max = ((RANS64_L >> 16) << 32) * freq        // = 2^47 * freq
if (x >= x_max) { 吐出 (uint32)x; x >>= 32; }  // ← 注意是 if，不是 while
x = (x / freq) << 16 + (x % freq) + start
```

**符号表是"栈"**：C++ 正向建表，**反向遍历编码**，`flush` 先吐 state 高 32 位、再吐低 32 位。
→ **硬件必须解决"逆序"问题**（见 §四）。

## 三、实测得到的硬件关键数（`rans_oracle trace`，2026-09-18）

| 量 | 64 符号 | 4096 符号（压力） | 对硬件的意义 |
|---|---|---|---|
| 编码符号总数（含 bypass） | 69 | 4,242 | — |
| 逃逸次数 | 2 | 134 | 真实数据实测 0 次，硬件只需**不优化的兜底** |
| **单符号最多重归一化** | **1** | **1** | ✅ 状态机里是**一次比较 + 至多吐 1 个字**，不是循环 |
| 重归一化发生率 | 14.5% | **14.9%** | 85% 的符号不吐字节 → 输出是**突发式**的 |
| **`freq` 范围** | 1 ~ 65533 | 1 ~ 65533 | 16 位；**`freq = 1` 必须能算** |
| **商 `x/freq` 有效位宽** | 16 ~ **46** | 16 ~ **47** | 商很窄——**但这不决定除法器宽度** |
| **被除数 `x` 有效位宽** | — | **16 ~ 63** | ⚠️ **这才是除法器输入宽度 → 必须 64 ÷ 16** |
| state 范围 | `0x80000000` ~ `0x38ef…` | `0x80000000` ~ `0x7feb…` | state 寄存器 **64 位**（含中间量） |

> ### 🔴 更正（2026-09-18，代价：白跑一次派活）
>
> 本表初版把**商**的宽度当成了**除法器**的宽度，写成「商 ≤47 位 → **除法器做 48 位即可**」。
> **这是错的。** 送给除法器的是重归一化之后的 rANS state `x`，实测可达 **63 位**；
> 只有**商**才 ≤47 位。**除法器必须按 64 位被除数做。**
>
> **怎么被发现的**：oracle 生成的向量文件用了 `%012llx`（**最小**宽度而非固定宽度），
> `x` 超过 2^48 时自动变成 13 位十六进制，下游按固定列宽解析就错位 →
> C2a1 的对拍报出 1284 条"不匹配"。**而手算那条记录发现：错的不是 RTL，是被截断的输入。**
> 教训：**向量文件必须固定宽度**（已改为 `%016llx`），且**位宽结论必须区分"商"和"被除数"**。

> ⚠️ 这些数**只对当前 CDF 表和当前分布成立**；换表要重跑 oracle 复核。

**重归一化保证的不变式**（`Rans64EncPut`: `if (x >= x_max) x >>= 32`，`x_max = 2^47*freq`）：
送给除法器的被除数**恒满足 `x < 2^47 * freq ≤ 2^63`**。
已在 24,492 条真实轨迹上复核：**违反 0 次**。
这条不变式正是 §四 里"一次修正就够"的误差界来源，**换任何一种 renorm 方案都必须重新验它**。

## 四、⚠️ 本设计的两个真难点

### 难点 1 · **除法延迟 = 吞吐率上限**（最关键）

rANS 的状态更新是 **`x' = f(x, freq)` 的跨符号串行依赖**——
**下一个符号必须等上一个符号的 state 算完，无法流水线。**

所以「每符号多少拍」≈「除法器多少拍」，**吞吐率被除法器卡死**。

按 **393,216 符号/帧**（Kodak 768×512 **基准**口径；⚠️ **部署口径是 256×256 = 65,536 符号**，
见 `07_数字口径表.md` §1.5）、**100 MHz**、被除数 **64 位**：

| 除法方案 | 每符号拍数 | @393,216 符号 | @65,536 符号 | 纯每符号 | 状态 |
|---|---|---|---|---|---|
| 逐位 restoring（64 位） | **66（实测）** | **259.5 ms** | **43.3 ms** | 660 ns | ✅ C2a1 已实测 |
| radix-4（2 位/拍） | ~32 | ~134 ms | ~22 ms | ~320 ns | 估算 |
| radix-16（4 位/拍） | ~16 | ~71 ms | ~11.8 ms | ~160 ns | 估算 |
| **倒数 + 乘法 + 一次修正** | **5（实测）** | **19.66 ms** | **3.28 ms** | **50 ns** | ✅ C2a2 已实测 |

**和 A53 比 —— ⚠️ 必须同口径。A53 的 73~146 ms 是 `256×256`（65,536 符号）的：**

| 口径 | A53 的 AE（外推） | C2a1（660 ns/符号） | C2a2（50 ns/符号） |
|---|---|---|---|
| **纯每符号** | 283.5 ~ 567 ns/符号 | **慢 1.16 ~ 2.33×** | **快 5.7 ~ 11.3×** |
| **@256×256（部署口径）** | 73 ~ 146 ms | **快 1.7 ~ 3.4×** | **快 22 ~ 45×** |

> 📌 **结论：必须走"倒数 + 乘法"路线。**
> 判据是**纯每符号**那一行 —— rANS 是跨符号串行依赖，**吞吐率就等于每符号延迟**，与分辨率无关。
> 在那把尺子下，C2a1 的 660 ns **确实**比 A53 的 283.5~567 ns 慢 1.16~2.33×，
> 而 C2a2 的 50 ns **快 5.7~11.3×**。
>
> 🔴 **更正（2026-09-18）**：本节此前写「C2a1 的 259.5 ms 比 A53 的 73~146 ms **还慢 1.8~3.6 倍**」，
> 那是**跨口径比较**（393,216 符号 vs 65,536 符号），**不成立**。
> 同口径下 C2a1 在整图口径**反而更快**，只有在纯每符号口径才更慢。
> **「结论对、证据错」比「结论错」更危险** —— 答辩时被追问一次就塌。
> 详见 `07_数字口径表.md` §1.5(d)。

#### 已证死的精确除法方案（C2a2，2026-09-18）

```
rcp = (2^64 - 1) / freq            // 无符号 64 位整数除法，向下取整
q0  = (x * rcp) >> 64              // 128 位乘积取高 64 位
r0c = (x - q0 * freq) mod 2^17     // 只保留低 17 位
if (r0c >= freq) then q = q0 + 1, r = r0c - freq
else                 q = q0,      r = r0c
```

**为什么一次修正就够**：设 `2^64 - 1 = rcp*freq + e`，`0 ≤ e < freq`，则

```
x*rcp/2^64 = x/freq - x*(e+1)/(freq*2^64)
```

误差项 `< x/2^64 < 1`（实测 `x < 2^63`，见 §三），所以 `q0` **只可能是真商 `Q` 或 `Q-1`**。
又因为此时 `x - q0*freq < 2*freq ≤ 131066 < 2^17`，**第二次乘法只需要低 17 位**。
`freq = 1` 时 `rcp = 2^64-1`、`q0 = x-1`，修正后正好回到 `x` —— **不需要给 freq=1 开特例**。

**验证（Python 大整数，独立于任何 RTL）**：

| 检验 | 例数 | 结果 |
|---|---|---|
| 真实轨迹（`_logs\rans\divvec_p1.txt`） | 24,492 | **0 失配**；`Q-q0` 最大 1；修正命中 297 次（1.213%） |
| 全 `f∈[1,65535]` × 3 组极端被除数 | 196,605 | **0 失败** |
| 随机模糊（1/2/3 三种取值域） | 300,000 | **0 失败** |

**判据不变**：`q` 与 `r` 必须**逐位精确**（rANS 不容许任何近似，错一位整个码流就废）。

**倒数从哪来**：CDF 表是**固定的**（`GLC_NUM_CDFS=64` 行、`GLC_CDF_ENTRIES=27256` 项），
每个 `(行 k, 值 v)` 条目的 `freq` 是常量，所以 `rcp` 可以**离线算好、和 `(start, range)` 一起进 BRAM**
（表变大，见 §五）。RTL 的 `rans_div_rcp` 只把 `rcp` 当输入端口，不自己算。

> 🔴 **`rcp` 必须用 `(2^64-1)/freq`，不能写 `2^64/freq`。**
> 后者在 `freq=1` 时等于 `2^64`，64 位存不下 —— 会静默变成 0，然后除零。
> PS 侧建表（C2d）和 tb 里的参考值**都必须用同一个式子**。

### 难点 2 · **逆序** —— ⚠️ 这里有**两个**不同的逆序，混起来一定设计错

rANS 是栈。**「逆序」在这套设计里指两件互相独立的事**：

#### ① 符号顺序（**上游问题，C2c 不管**）

符号表按**图像顺序**压入，编码时必须**从最后一个开始** → PL 消费符号的顺序 = 图像顺序的**逆序**。

- 丢给 PL 的符号流**必须已经是编码顺序**（谁去反都行：PS 写 DDR 时倒着写，或 PL 从 DDR 倒着读）。
- 393,216 符号 × ~18 bit ≈ **0.9 MB → 只能放 DDR**，别试图塞进 BRAM（9.3 Mb = 1.16 MB，还要放 CDF 表）。
- ✅ **C2c 的 `rans_enc_stream` 不管这件事**：它的 `s_valid/s_ready` 流**假定已经是编码顺序**。

#### ② 输出字节方向（**C2c 实现的就是这条**）

`Rans64EncPut` 是 `*--ptr = word`，**写指针从缓冲区末尾往前走**。

- 硬件照做：`mem[ptr-1] <= word; ptr <= ptr-1;` —— 写指针递减，很便宜。
- 最后 `flush` 再吐 2 个字，**顺序容易搞反**：两次 `*--` 之后内存里是
  **低字在前、高字在后**（`mem[p-2]=x[31:0]`，`mem[p-1]=x[63:32]`）。
- `payload = [ptr, DEPTH)`，**缓冲区大小不影响 payload 内容**。
- 真机上这块缓冲在 DDR —— 好在小：768×512 q0 的码流只有 **1,302 B**。

> ⚠️ **逐帧**做还是**逐子图**做会影响缓冲大小与流水线划分，属待定项（见 §六）。

## 五、CDF 表与倒数表（BRAM 预算）

**实测表结构**（2026-09-18，直接解析 `assets\板端代码\glc_cdf_table.h`）：

| 量 | 值 |
|---|---|
| 行数 `GLC_NUM_CDFS` | 64 |
| 总项数 `GLC_CDF_ENTRIES` | 27,256 |
| `(start, range)` 对数（= 每行项数 − 1，末项固定 65536） | **27,192** |
| `range` 取值范围 | **1 ~ 65,533**（不会出现 65,536，uint16 安全） |
| **不同 `range` 值的个数** | **949** ← 关键数字 |

| 方案 | 容量 | 占 9.3 Mb BRAM | 出处 |
|---|---|---|---|
| 照抄参考实现的**填充表** | 6.12 Mb | **68.99%** ❌ | `assets\板端代码\README.md:103` |
| **紧凑 CDF 表**（行长表 + 紧凑数据 + 行起始偏移） | 0.87 Mb | **9.38%** ✅ | 同上（实测 109,024 B） |
| ＋ **倒数与 CDF 同址**（每项加 64 位 `rcp`） | +1.74 Mb | **合计 28.1%** | ⚠️ 本规格新增，按 27,192×64 bit 算 |
| ＋ **分级倒数**（每项加 12 位序号 + 949 项×64 位倒数表） | +0.39 Mb | **合计 13.5%** | ⚠️ 本规格新增，**待 C2d 精算** |

> 倒数表**只有 949 个不同取值**，所以"分级"方案（每项存一个序号，真正的倒数表单列一张小表）
> 比"同址"方案省 ~1.35 Mb。**代价是多一级查表与流水。**
> 两种方案 RTL 侧的接口**完全相同**（都是把 `rcp` 当输入端口），
> 所以**这个选择可以推迟到 C2d**，不影响 C2a2。

索引方式固定为：`row = &GLC_CDF_FLAT[GLC_ROW_START[k]]`。

**`k = glc_build_index(scale)` 是否放 PL**：待定。它需要浮点比较/查表，
**建议放 PS**（PS 本来就做矢量量化与调度），PL 只接收 `(k, value)` 或 `(start, range, rcp)`。

## 八、实施顺序（每步都要仿真过）

| 步 | 模块 | 判据 | 状态（**每符号拍数才是吞吐率口径**，见 §四） |
|---|---|---|---|
| **C2a1** | `rans_div` —— 逐位 restoring 基线（被除数 64 位） | 与向量逐位相符；报出每符号拍数 | ✅ **过**：24,499/24,499，**66 拍 = 660 ns/符号** |
| **C2a2** | `rans_div_rcp` —— 倒数乘法 + 一次修正 | 同上，且 cycles ≤ 6 | ✅ **过**：270,121/270,121，**5 拍 = 50 ns/符号**（⚠️ **仅除法器**） |
| **C2b** | `rans_enc_put` —— 单符号状态更新 + renorm（**闭环**） | 与 oracle 的逐符号 trace **逐行一致** | ✅ **过**：**72,086/72,086**，**4 拍 = 40 ns/符号**（⚠️ 纯环延迟，端到端不可达） |

### 8.2.3 ⚠️ 三条设计约束（实测得出，必须写进接口约定）

| # | 约束 | 依据 |
|---|---|---|
| 1 | **`d_value` 必须按「有符号 16 位」处理** | 实测真实符号范围 **[-2, 3]**（**有负数**），而 `CDF_OFFSET` 全为负（[-1565,-1]），`v = sym - OFFSET` 必须按有符号算 —— **我第一版按无符号写，是个 bug** |
| 2 | **`n_bypass` 最大 4**（16 位输入下） | `raw_val ≤ 2×(32767+1565) ≈ 68664 < 2^20` ⇒ 最多 5 个 4bit 组里实际到 4 |
| 3 | **`out_of_domain`（n_bypass > 7）在本位宽下不可达** | 由上一条推出 ⇒ 那段是**安全网**，可在后续优化中删掉 |

### 8.2.4 ⚠️ 最容易搞错的点：**顺序**

C++ 是 `syms.push_back(...)` 之后 **`pop_back` 倒序编码**（rANS 是栈）。展开到逻辑符号层面：

```
逻辑符号按 i = n-1 → 0 处理；                ← 所以 PS 必须**倒着写** DDR
每个逻辑符号内部按 [r_{n-1} … r_0, b_last, b_hi×m, 主] 发射
```

⇒ 给 RTL 的 `_logical.txt` 要按 **i = n-1 → 0**；
RTL 发射的 `_rans.txt` 是 **reverse(seq)**。
**`s_last` 只挂在主符号上**（每个逻辑符号的最后一次发射永远是主符号）。

> `gen_c2d_vector.cpp` 的注释里写死，**不要再改回去**。
