# 电台发送记录

> 每次实发都往这里追加一行。**这是"我们确实把图发出去了"的可核查物证**，
> 也是答辩时说清"发了什么、对方收到什么"的依据。
>
> 对方（B 端）核对时，只要比 md5 即可。

## 2026-09-22 · A 板 → 电台 · 第 1 次四张会话

| 项 | 值 |
|---|---|
| 图源 | `E:\fudanwei\photo\` 前 4 张（微信图片 `..._479/_480/_481/_482_23.jpg`） |
| 板上路径 | `/root/photo/p1.jpg` ~ `p4.jpg`（与本机**逐字节一致**，md5 已核对） |
| 电台 | TP5603-D100，`/dev/ttyUSB0`，470.110 MHz，19.2 kbps，115200 8N1 |
| 协议 | 会话模式（`A_send_session.py`，N=4，BEGIN 里列长度） |
| 编码方式 | 常驻批处理（`--batch`） |

### 电台自检（实测）

```
AT+FREQ?    -> FREQ:470.110MHz OK
AT+SYMBOL?  -> 19.2 kbps@9.6 khz OK
AT+UART?    -> UART: banud:115200, dataBit:8, stop:1, check:N OK
AT+EXIT=1   -> 'OK'          （进入透传模式）
```

### 会话过程（实测原文）

```
① SESSION_BEGIN  N=4  逐张长度=[328, 332, 320, 328]  ✅ 已确认（第 1 次，0.24 s）
② [1/4] p1.glc  328 B  OK  0.58 s（第 1 次）
   [2/4] p2.glc  332 B  OK  0.58 s（第 1 次）
   [3/4] p3.glc  320 B  OK  0.56 s（第 1 次）
   [4/4] p4.glc  328 B  OK  0.58 s（第 1 次）
   进度：已发 4/4 ｜ 已确认 4/4
④ SESSION_END  sent=4 ok=4   ✅ 已确认（第 1 次，0.22 s）
数据段耗时 2.31 s   共 4 张   成功 4   缺 0
SESSION_DONE  ok=4/4
```

### ★ 发给 B 核对的四行

| 序号 | 文件名 | 字节 | md5 |
|---|---|---|---|
| 1 | p1.glc | 328 | `c963bebf706c034bdbbc5cc4328dd7f9` |
| 2 | p2.glc | 332 | `6a8781ab4b78a7bc95b3e613bc603794` |
| 3 | p3.glc | 320 | `ee1a9fb4ce838512cf077aadf8bca239` |
| 4 | p4.glc | 328 | `2ea5d27f57dc6754477a3b122b46d2f7` |

### 耗时拆解（实测）

| 环节 | 耗时 |
|---|---|
| 预处理 4 张 | ~4 s |
| **引擎载入（冷启动一次性）** | **13.575 s** |
| 编码 p1 / p2 / p3 / p4 | 15.57 / 1.10 / 1.24 / 1.04 s |
| **电台发送 4 张（含 AT 自检 8.2 s）** | **10.6 s** |
| **合计（敲命令 → 发完）** | **约 35 秒** |

> 首张 15.57 s 是因为它含引擎载入；之后每张只要 ~1.05 s。

### 顺带确认

* 容器 md5 与**历史单张链完全一致** ⇒ 整条编码链是**确定性**的
  （同一张图跑多少次都出同一个容器）。
* 板上 `/root/photo/p1..p4.jpg` 与本机 `E:\fudanwei\photo\` 前 4 张
  **md5 逐一相同**，所以是用你的原图直接编的，没有中转损耗。

## 附录：怎么再发一次

```bash
# 板上（原图已在 /root/photo/）
bash /root/send_image.sh --batch /root/photo/p1.jpg /root/photo/p2.jpg \
                         /root/photo/p3.jpg /root/photo/p4.jpg

# PC 上（指着本地图片）
cd E:\fudanwei\GLC-共享包\工具\电台发图
.\发图.ps1 E:\fudanwei\photo\*.jpg
```

**发之前确认 B 端在监听**（`radio_rx_session.py`）；等不到会在约 30 s 后放弃，
**容器不会白发**。

### ⚠️ 本次暴露并修掉的一个 bug（我自己的）

`glc_batch_rsd.py`（PL 路径）写到 `/root/glc/batch_out`，
而 `glc_batch_cpu.py`（CPU 路径）写到 `/root/glc/batch_out_cpu` ——
**`send_image.sh` 里把产物目录写死成了 `batch_out_cpu`**。

⇒ 走 PL 路径时从错误目录找产物 ⇒ 误判"**还缺 p5 p6**" ⇒ **又用单张链重编了一遍（白跑 20 秒）**。
**最终容器是对的**（兜底那条链产出正确），但白等。

**已修**：产物目录跟着所选脚本走。复测确认不再触发兜底，
编码总耗时从 **28.2 s → 8.2 s**。
