## 0. 一句话

**s4（生成器）的 int8 量化是真的坏了**：同一个输入、同一个后端，只换精度，
`PSNR(s4_int8 输出, s4_tf32 输出) = 24.07 dB`，而 `PSNR(s4_bf16 输出, s4_tf32 输出) = 55.55 dB`。
**bf16 几乎无损，int8 差 31 dB。**

**而且重编 per-channel 版后只涨到 25.04 dB（+0.97 dB）**
⇒ **per-tensor 不是主因，int8 本身撑不住 ⇒ s4 应直接走 bf16。**

**实验条件**：同一个输入文件 `calibref\calib\s4_gs_generator\00.ftmp`、

| s4 模型 | 输出 v_id | **PSNR vs tf32** | RMSE | 输出 std | 输出范围 |
|---|---|---|---|---|---|
| `compile2\s4_tf32`（参考） | 4091 | — | — | 0.0824 | −0.9443 … 1.2852 |

## 1. ★ 受控精度对比（核心证据）

**实验设计**：三个模型只有 `--qdtype` 不同（int8 / bf16 / tf32），
其余全部相同 —— 同一份 `s4_gs_generator_parsed`、同一份 `optimized`、
同一条命令、**同一个输入文件**、同一个 Host 后端、同一个 `--dump_format SFB`。

输入：`工作区\calibref\calib\s4_gs_generator\00.ftmp`（262,144 B = 1×256×16×16 fp32，即 y_hat）
输出张量：786,432 B = 1×256×256×3 fp32（重建图）

三条命令（从 `run_dump.txt` 里抄出来的原文）：

```
icraft-run.exe --json <OUT>\s4_gs_generator_quantized.json --raw <OUT>\s4_gs_generator_quantized.raw
               --input 工作区\calibref\calib\s4_gs_generator\00.ftmp --backends Host
               --log_path <OUT>\run_out\logs --dump_format SFB --dump_ftmp <id>
```

| 模型 | dump 的 ftmp id | 文件 |
|---|---|---|
| `compile2\s4_int8` | 4107 | `run_out\logs\s4_gs_generator\ftmpSFB\4107.ftmp` |
| `compile2\s4_bf16` | 4107 | 同上路径 |
| `compile2\s4_tf32` | 4091 | 同上路径 |

**实测结果**：

| 对比 | PSNR | RMSE |
|---|---|---|
| **int8 vs tf32** | **24.07 dB** | **0.13956** |
| bf16 vs tf32 | **55.55 dB** | 0.00375 |
| int8 vs bf16 | 24.15 dB | 0.13901 |

**输出张量自身统计（实测）**：

| | 取值范围 | std |
|---|---|---|
| tf32 | −0.9443 … 1.2852 | 0.0824 |
| bf16 | −0.9609 … 1.2812 | — |
| **int8** | **−0.7227 … 1.2402** | **0.1125** |

⇒ int8 输出**动态范围被压缩**（负端 −0.72 vs −0.94），同时**噪声更大**
（std 0.1125 vs 0.0824，**大 36%**）。

## 2. per-tensor 还是 per-channel？

**实测：我们全是 per-tensor；复旦微官方参考模型对权重用 per-channel。**

命令：`python 工具\量化复核\qscale_probe.py <ZG.json>`

| 模型 | 权重(params) | 激活(activations) |
|---|---|---|
| **官方 `yolov5s_plin_352x640_ZG.json`** | **57 per-channel** + 1 tensor + 3 other | 204 per-tensor |
| `compile2\s1_int8`（我们，`--per tensor`） | **166 全 per-tensor** | 1684 per-tensor |
| `compile_perch\s1_int8`（我们，`--per channel`） | **77 per-channel** + 89 tensor | 1684 per-tensor |
| **`compile3\s4_int8_real40`（出厂版 s4）** | **197 全 per-tensor** ⚠️ | 2247 per-tensor |
| `compile2\s2_int8` | 30 全 per-tensor | 135 per-tensor |
| `compile2\s3p1_int8` | 24 全 per-tensor | 172 per-tensor |

**per-channel 的收益有多大（s1 实测）**：
一个权重张量内部，通道间 scale 的极差（max/min）中位 **3.56×**、p90 **7.35×**、最大 **29.16×**。
⇒ 通道间量级差 3.5~29 倍，用**一个** per-tensor scale 必然要么削顶要么浪费位宽。

**可行性已验证**：`compile_perch\s1_int8` 是**跑通了**的
（`icraft-generate` 出了 ZG.json，per-channel scale 保留在模型里）
⇒ ZG330 后端**支持** per-channel。
（注意：`--per channel` 在 s1 上只把 166 个权重张量里的 77 个变成 per-channel，
其余 89 个仍是 per-tensor —— 工具自己会挑。）

**定量**：`s4_gs_generator_quantize_mix_config.csv` 里 659 行 op，
`per` 列**全部**是 `tensor;tensor`，`saturation` 全部 `kld;kld`，`dtype` 657 int8 + 2 fp32。

## 3. 标定集：8 张 → 40 张真实照片改变了什么

命令：`python 工具\量化复核\scale_diff.py <A_ZG.json> <B_ZG.json>`

| 指标 | 实测 |
|---|---|
| 可比 per-tensor scale 条目 | 2444 |
| 逐字节相同 | 197（8.1%） |
| 相对变化 中位 | **13.0%** |
| p90 / p99 / 最大 | 34.4% / 71.7% / **163.3%** |
| 变化最大的张量 | op 43~48，scale 0.417835 → 1.1002（+163%） |

⇒ **标定集确实实质改变了量化**（不是只动几个字节），但**幅度是中位 13% 量级**，
与我们需要的量级（把 24 dB 拉到 45 dB，即误差降 11 倍）**差得很远**。

**B 端实测对照**（他们给的数）：int8 旧 9.99 dB → int8 新 19.95 dB。
⇒ 换标定集**确实救回了 10 dB**（旧 8 张模型是真的坏），但**到 19.95 就平了**。

## 4. 48 样本崩溃：工具其实给了开关

`icraft-quantize.exe --help` 的原文选项（**实测**）：

```
--batch      Calibrating in batch mode to save memory   [default: 1]
--bin_num    Setting the bin numbers when calculate saturation point [default: 4096]
--per        The quantization size in layer-wise or channel-wise
--saturation The method to determine saturation
--autoqset_num / --smooth_alpha / --mix_precision / --asymmetric / --before_relu / --input_norm
```

`quantize.log` 头部（8 张那次）**实测**原文：

```
[I] Calibration Set Size: 8
[I] Batch Number: 1
[I] Batch Size: 8
[I] Saturation Method: kld
```

⇒ **`Batch Size` = 样本数**，也就是说**8 张标定样本是一次 forward 全塞进去**的。
56 张就是一次塞 56 张，激活内存 ≈ 7 倍。
**48 张崩（0xC0000005、只在 74 s 就崩、不是内存不足）与"一次塞太多"高度吻合，
而 `--batch` 正是官方给的"分批省内存"开关 —— 这就是绕开办法。**

⚠️ **未实测**：我没有跑过 `--batch`。`c1_pipeline.py` 也**没有暴露** `--batch`
（L117-125 构造的命令里没有它）。要试的话加一行即可。

## 5. 逐层误差（初步，配对是近似的）

命令：`python 工具\量化复核\q3_layer.py <int8_ZG.json> <tf32_ZG.json> <00.ftmp> <outdir> 16`

配对办法：用 `difflib` 按 `(op 类型, 输出张量形状)` 对齐两个模型的 HardOp 序列。
**只对齐上 122 / 1116 个 op**（int8 有 111 个 Conv2d、tf32 只有 83 个 ⇒ 图结构本来就不同）
⇒ **这条链的配对不可靠，只能看趋势，不能当逐层结论。**

| int8 op 序号 | 类型 | 形状 | PSNR | SNR |
|---|---|---|---|---|
| 93 | TransposeNode | 1x16x1x512x16 | 40.01 | 14.64 |
| 115 | ReshapeNode | 1x16x1x512x16 | 35.43 | 13.92 |
| 141 | TransposeNode | 1x1x16x512x16 | 37.74 | 12.30 |
| 168 | AddNode | 1x1x512x16x16 | 34.72 | 13.28 |
| 215 | MultiplyNode | 1x1x512x16x16 | 36.47 | 13.43 |
| 241 | ReshapeNode | 1x1x512x16x16 | 39.70 | 13.46 |
| **255** | ReshapeNode | 1x2x1x4096x16 | **23.12** | **−2.74** |
| 279 | TransposeNode | 1x512x1x16x16 | 32.03 | 16.11 |
| 306 | TransposeNode | 1x16x1x512x16 | 37.24 | 11.27 |
| 328 | ReshapeNode | 1x16x1x512x16 | 31.12 | 9.43 |
| 375 | TransposeNode | 1x1x16x512x16 | 32.63 | 8.05 |
| 401 | AddNode | 1x1x512x16x16 | 37.42 | 8.45 |
| 428 | MultiplyNode | 1x1x512x16x16 | 30.89 | 9.07 |
| 475 | ReshapeNode | 1x1x512x16x16 | 32.80 | 9.76 |
| **488** | ReshapeNode | 1x2x1x4096x16 | **14.53** | **−0.00** |

> `SNR = 10·log10(mean(y²)/mse)`，即**误差功率相对于信号功率**。
> **SNR ≤ 0 dB ⇒ 误差功率 ≥ 信号功率 ⇒ 该张量被量化噪声淹没。**
> idx 488（PSNR 14.53 / SNR ≈ 0）就是这种情况。

⇒ **趋势**：误差**沿深度单调放大**（14.6 dB → 8~9 dB SNR），并不是集中在某一层，
   而是在中后段**持续劣化**，到 idx 488 已经 SNR=0。

## 6. 编码端 vs 解码端：把责任分清楚

**历史实验 `recon_real24` / `e2e_zg_int8` / `e2e_recon_bf16` 的图标题写得很清楚：**

> 图 `v8\quant_compare.png` 标题 = **"GLC 编码端量化对比（真 Kodak，256×256 裁剪，q0，S4 保持 fp32）"**

⇒ **那一整批实验里 S4 固定 fp32**，它们量的是**编码端（s1/s2/s3）**的量化。

它们的结论（**实测**，24 张 Kodak，bpp≈0.0263）：

| 链路 | 平均 PSNR |
|---|---|
| fp32 参考 | 20.62 dB |
| ZG int8 链（**S4 保持 fp32**） | 20.11 dB |
| ZG bf16 链（同上） | 20.66 dB |

⇒ **编码端的 int8 只值 0.5 dB，几乎无损。**
⇒ **结合 §1：整条链的问题集中在 s4 的解码端 int8，不在编码端。**

（`recon_real24` 逐图数据，实测：int8 20.33 / bf16 20.56 / fp32 20.58 平均，
  kodim01 18.57/18.69/18.57，kodim13 15.78/15.85/15.93 —— 三者肉眼无差别。）

## 7. RD 曲线：这套编解码器在这个码率下本来能到多少

`v8\rd_curves.png`（数据来源 `v7_kodak\v7_bitstream.json`，真 Kodak 24 张，768×512 / 512×768，
bpp 按**整包含 76 B 头**计）：

| q | bpp | PSNR |
|---|---|---|
| q0 | 0.0263 | **21.34 dB** |
| q1 | ~0.031 | ~21.73 dB |
| q2 | ~0.035 | ~22.08 dB |
| q3 | 0.0388 | **22.25 dB** |

⇒ **在这条 bpp≈0.026~0.039 的曲线上，PSNR 的工作区间就是 21~22 dB。**
我们的容器（328~340 B / 256×256×3 ⇒ bpp≈0.040）落在这条曲线的同一区间。
**所以"20 dB"本身不是 bug —— 它是这个码率下这套模型的正常水平。**

⇒ **要拿 ≥38 dB，必须落在 bpp 高得多的点上（或换更高效的模型），不是改量化能解决的。**

## 9. 诚实清单（含我自己的错）

1. ★ **我中途错过一次**：先看到 `recon_real24`（int8 20.33 / bf16 20.56 / fp32 20.58）

   **那是错的** —— 那批实验的图标题写明 **"S4 保持 fp32"**，量的是编码端。
   发现后立刻用 §1 的受控实验重测，得到 **int8 vs tf32 = 24.07 dB**。本文以 §1 为准。
2. ★ **撤回 42 号文档 §三的"最大 scale=153.901 ⇒ 动态范围 ±19545"**。
   `@scales` 的乘/除语义（`x = q/scale` 还是 `x = q*scale`）**我没有验证过**，
   从 scale 反推动态范围是不成立的推断。**结论作废，只保留"动态范围可能过大"这个方向性猜测。**
3. §5 的逐层配对**不可靠**（只对齐 122/1116，int8 与 tf32 的图结构本来就不同），
   只能看趋势，**不能当"误差集中在某几层"的证据**。要钉死需要能稳定配对的办法。
4. `--batch` **我没有实测过**，只从 `--help` 和日志里的 `Batch Number/Batch Size` 推出来。
5. **`41.71 dB` 我既没复现也没能解释**，只能指出它与实测 RD 工作点差 ~20 dB。
6. `per-channel` 重编在写本文时**还在跑**（`compile4\s4_int8_perch`，
