# B端实现步骤与改进历程

本表串起DSH早期工作与Codex后续任务。日期代表对应文档或阶段，不把历史快照文件的复制时间当开发完成时间。每一阶段的完整脚本、日志和原文保存在`../02_源资料归档`；来源与SHA256可由清单反查。

## 1. 基础环境与GLC复现（9月阶段）

| 步骤 | 解决的问题与做法 | 验证及边界 |
|---|---|---|
| 环境建立 | 检查Python、torch、compressai、ICraft和厂商示例；纠正早期“Windows装不了compressai”判断，后来实际安装1.2.8 | 固定环境原位保留，不把venv复制当可迁移安装 |
| 官方源码和权重核对 | 固定GLC仓库、checkpoint及本次核到的GLC主仓许可证，建立原图→编码→解码参考 | 当前来源核对与第三方清单单独保存，复用模型明确署名；未宣称传递依赖全部完成授权核查 |
| 固定数据集 | Kodak24真图像，按q0～q3生成基准 | 96条、96唯一键；18横图和6竖图，按整图像素算bpp |
| 拆图与工具链 | 导出S1/S2/S3/S4子图，做ICraft适配/生成，保存校准输入与dump | 各阶段日志可能有失败/重跑，不能把最终产物存在理解为第一次全绿 |
| Host对照 | 逐子图fp32校准输入、HostBackend输出与重建图对比 | 局部/静态灌回验证，不是同码流完整量化解码或实板速度 |
| rANS契约 | 固定CDF、scale索引、符号顺序、状态字和bypass格式，准备ROM/向量 | 为后续PS/PL逐符号核对建立参考 |

YOLOv5、ResNet18和基础约束练习是工具链预研。其结果用于说明环境熟悉过程，不计作GLC回传主系统已部署功能。早期平台、FPGA与NPU能力解释中推测性内容以之后工程和实测为准。

## 2. 上板、无线与全闭环（9月底至10月上旬）

| 步骤 | 原问题 | 实施与结果 |
|---|---|---|
| PS/PL/NPU通道 | 模型与板端输入输出、地址、DMA和工具链使用尚未贯通 | 通过厂商示例、独立探针和子图测试建立真实上板路径；代码/日志区分成功与超时 |
| HDMI显示 | 最初只能电脑看结果 | 打通帧缓冲与FPGA扫描，形成板上出图；后续独立处理颜色与欠载 |
| USB电台 | Lite板环境缺CH340匹配驱动 | 构建/安装适配内核的usbserial/ch341模块，完成AT控制、透传和帧收发 |
| 真实GLC过空口 | 需要证明不是仅传测试字符串 | 保存发送前/接收后的真实容器、双向校验和电脑解码结果 |
| 板端熵解码 | 需要摆脱电脑rANS | 从纯Python实现对拍，接入生产C扩展与固定表 |
| S4分段 | 完整生成网络存在部署/内存约束 | 切分、编译并逐段上板，形成S4五段主路径及高精度回退 |
| SD输入全板闭环 | 依赖电脑参与编码/解码流程 | 实现板端读取图片、编码、解码到HDMI；当时通过PS熵编码绕过编码位流与显示位流冲突，不称整链全PL |

历史约64.6/69.5秒全闭环属于当时版本和测量范围，与当前单张纯解码时间不同。操作卡中旧IP、布局和路径作为历史资料，部署入口以当前版本为准。

## 3. 独立PL rANS解码器（10月阶段）

从算法契约出发，完成CDF/搜索、区间更新与归一化、控制和流接口，再加两桶快路径、六状态单符号核和行信息预取。六状态包括IDLE/MUL/ADD/REF/REF2/OUT，不能写成每拍接收一个新符号的六级流水。使用真实四相位向量逐符号比较，同时测试escape/bypass与边界。固定最终五份RTL并进行独立综合、实现、资源和功耗估计。

本次重新读取历史输出核查：C版40份输出与相应向量逐int32比较均一致；四份PL日志65,536个符号均一致；五个escape日志820个符号均一致。C版测试中已覆盖的escape范围与PL范围分别陈述，不把一个测试集的通过借给另一路实现。

最终独立IP源、实现报告和交付快照之间通过SHA256绑定。不同`verify_pkg`旧stream源码不冒充最终版本。内部200MHz约束下WNS+0.356ns，报告仍有83输入和85输出未设I/O delay，故尚非外部接口和整机集成时序签核。生产解码仍用PS C扩展。

## 4. 解码稳定性与性能演进（10月中旬）

| 问题 | 改进 | 采用/局限 |
|---|---|---|
| 部分S4 fp16中间输出异常 | 检查有效性，对特定段以tf32重新计算 | 生产保留分级回退；没有保证所有可能输入永不出现数值异常 |
| 每帧反复加载模型 | 进程内常驻会话、复用模型，处理逐forward设备复位与结果生命周期 | 稳态从早期约40秒降至约5～6秒的历史记录，按当时版本引用 |
| 多客户端硬件争抢 | flock硬件锁、唯一写屏者、解码busy状态、目录事务 | 调用方仍需检查锁是否真正取得；不能说加锁绝对杜绝故障 |
| 多会话接收失败 | 单次脚本改常驻、串口只初始化一次、按会话号保存 | 修复A队列第二张BEGIN无人接收与同名覆盖 |
| 异常或失联 | 状态账本、残留标记清理、无进展检测、备份与恢复 | 有保护机制不等于完成长期稳定性验收 |

10月16日已有A端真实多张队列收发证据。10月20日出现解码异常、最小探针失败并进行全量备份；曾怀疑NPU/驱动/DDR环境，但没有足够交叉试验确认物理损坏。后续恢复成功不能反向把所有故障归因到已证明的同一个硬件问题。

## 5. 解码恢复、准备与交互（10月20—21日）

1. 冻结异常现场、源码、位流和数据，恢复已验证解码路径并按固定样例对拍。
2. 恢复普通热态约5～6秒后，继续优化引擎与初始化，普通图降至约2.6～2.8秒、双回退约4.7～4.9秒；各批次分别留日志。
3. 将普通与备用的准备分开观测，预加载备用以缩短首次回退等待；不把热态耗时当上电耗时。
4. 实现点图放大和返回，通过去除重复刷新、缓存与轻量推屏提速；用户确认响应更快、放大返回正常。独立输入采集线程在后续10月23日管理界面阶段实现，日期不混用。
5. 对准备时间的RAM缓存和后台重叠试验做正反对照，退步的尝试撤回。

本阶段完整记录见原文`codexwork/01_文档/20261020_*`、`20261021_*`及相应工程/验证目录。28/4/1布局为历史版本，后续已改21图。

## 6. 绿点排查、原生显示与启动（10月21—23日）

| 对照/改进 | 观察与结论 |
|---|---|
| 静止原图、软件帧与实屏比较 | 软件PNG无对应闪点，实屏绿色位置固定但闪烁 |
| 长短线、大小屏、电脑输出 | 短线有改善；同板同线大屏正常、小屏接电脑正常，说明链路适配需继续核查 |
| 供电、编码、滤波、倍频、时钟相位 | 多候选解码/显示回归通过，但用户绿点反馈基本相同，未作为修复成功 |
| 1080p30 | 小屏黑屏或异常，已回退，不能写低刷新率方案被采用 |
| 新小屏与EDID | 1024×600原生输入，电脑活动信号50.25MHz；据此适配本板扫描和时钟 |
| 原生位流 | 1024×600、50.25MHz、总1344×625，用户确认绿点消失、稳定 |

| 四阶段启动 | 首帧先出、受锁保护并行准备、无损只读模型镜像、失败fallback |

## 7. 红图离线定位与512新增（10月23—24日）

用户报告最新图全红后，保存来图、板端PNG、模型/常量与日志，分别对照原图、Host INT8先验、原始PyTorch与历史ONNX。13次来图去重9份电脑复解均完成，红图在电脑复现；相同输入各路径CDF索引存在兼容差异，字节往返自洽不足以证明与发送端兼容。

本地控制样本证明约3e-8尺度差可跨0.11边界、改变一个CDF索引并破坏字节往返。仅用已知控制参考纠正该索引能恢复原字节，属于因果诊断，不是可部署的通用修复，也未证明真实红图就是此处所致。继续需要发送端同一GLC、实际模型和正常脚本。

新增512根据A侧90/91文档实现四块顺时针接收、完整发布、同引擎逐块解码与无损粘贴。补入图库尺寸、单张计数、整包删除恢复和原子性约束，沿用原模型/位流。离线协议、PTY、界面/批处理、安装回滚共197条断言通过；另四真实码流电脑解码16段往返及四象限像素一致。PNG尺寸检查增加文件身份缓存，避免每次图库刷新反复完整读取512PNG；完成解码时仍做完整校验。

v1封包后发现校验开销并补缓存，最终交付v2；v1保留历史，不用于部署。512部署入口包含默认真实NPU对拍，但尚未实际执行；候选保持明确状态。

## 8. 当前收尾原则

冻结已采用功能，保留源文件与验证摘要；完成512实板/空口、颜色异常对照、最终冷启动和混合连续批次后补齐报告结果。工程、数值验证、光学反馈和质量指标分别证明对应结论。所有失败、回退和AI纠错保留记录，体现真实决策依据。
